**D186's messages** (commit "an error at a form of D186 says how it was read"). An error whose place overlaps a name, `<`, two or more type arguments, `>` and a call's `(…)` gets a note, from the loader (`with_reading_notes`, on parse and module errors from `load_program_opts` and on type errors from `type_errors`), which lexes the error's file again: only on an error's way, so a program that checks pays nothing. In a call's arguments: ``note: in a call's arguments `a < p.x, c > (d)` is a call of 'a' with the type arguments `p.x, c` (D186); for two comparisons, write `(a < p.x), c > (d)` ``; in a list, map or tuple literal: ``note: in a list, map or tuple literal `pair<P, Q>(p, q)` is two comparisons, `pair < P` and `Q > (p, q)` (D186); for a call with type arguments, give it a `let` of its own: `let v = pair<P, Q>(p, q)` ``, each underlining the form. **The look-ahead budget** (commits "no budget of tokens…" and "chains counted by the expression"). No budget of tokens: `type_args_then` follows a `<` until it closes, at most `MAX_NESTING` (256) deep, as a type nested deeper doesn't parse. A run of comparisons stays linear: of two scans that pass a token the earlier is deeper there, so at most 256 pass any token. Test first: `type_args_ahead`'s cases for a tuple of 64 and of 1,000 types and a type 70 and 255 deep (true; 256 deep false) failed before (four of them); `tests.burn.test_selfhost_parser.SelfHostedParserParity.test_type_arguments_have_no_budget_of_tokens` runs `mk<(int × 200)>(1)` and `mk<B<…60 deep…>>(1)`. The review's `budget_64.my` and `deep_43.my` print `1` (before: `generic function 'mk' cannot be used as a value`), and the checker lane's `mk<65-deep type>(x)` checks and runs. `test_a_long_run_of_comparisons_parses_in_linear_time` passes; 32,000 comparisons in a call take 0.32 s to check (0.11 s with the budget, 13 s before [[MYLA-416]]).

**A chain of 16,000 operands**: an expression may have at most 8,192 binary operators, casts, calls, indexes and fields outside its brackets, with those of the expressions it is in (`MAX_CHAIN`, `Parser.chain`, counted by `chained` and given back by `expression_with`; the count is never less than the depth of the tree they make). Past it: `parse error: more than 8192 operators, calls and fields in one expression: split it with a 'let'` at the one past. Test first: `test_a_long_chain_of_operators_is_a_parse_error` (4,096 `x < y` joined by `&&`, 8,193 `x` joined by `+`, `x` and 4,096 `.abs()` check and run; 16,000 of each and one more are the parse error at its place): before, `runtime error: stack overflow` (the checker, `infer_binary`, 61,000 frames deep). `and_16000.my` is the parse error. 8,193 `+` in an `async fun` run interpreted in a task, by `myla test`, and built for x86-64 (plain and `--checked`), aarch64 (under qemu) and wasm32 (under Node): all print 8193. Counting at each of the thirteen levels of precedence instead cost 0.26 % of the std.http check; counting by the expression costs nothing measurable.

## Decisions proposed

1. **No budget for the type-argument scan, a bound of depth instead** (the task's "a message that names the budget, or no budget"). Recommended as built: the depth bound is exact (deeper doesn't parse) and keeps the parse linear. The alternative, a message naming the budget, can't be given where the scan gives up, as a long run of comparisons is valid there.
2. **A chain's limit is a parse error at 8,192 per expression.** Alternatives: a checker, interpreter and lowering that walk a chain without recursion (other lanes' files, a larger change), or a larger limit (the checker overflowed at about 13,000 on an 8 MB stack). 8,192 leaves room on every runner measured; generated code with longer expressions splits them with `let`s.
3. **D186's note comes from the loader, which lexes the file again on an error**, not from the parser, which would need the forms it read carried to the checker's errors (the AST or the checker's files). Recommended as built: zero cost when there is no error, and one place for parse, module and type errors.
