Work package R7 of [[Project/Review-2026-11-12]]. Files: `lib/std/http.my`, `tests/burn/test_http.py`. The other half of [[MYLA-468]], which declared it as what remains.

- [x] **One byte per socket stops a default server** (high). 64 connections each send `G` and nothing more, renewed every 19 s: a normal request went unanswered for the 38 s watched (`python3 t_onebyte.py ./server` in `repro-r5/http/`, with `h.py` and `server.my`). The same with 200 header dribblers against 2 workers, even with `read_ms` 2,000: each freed worker takes the next dribbler (`t_park2.py`, case 3). A connection whose request has begun holds a worker for `read_ms`. Keep the parser with the parked socket and park again while a head is incomplete, so that a worker is held only for a complete head or an arriving body; or cap the workers that partial heads may hold (`serve_ready`, `read_request`)
- [x] The client keeps `Proxy-Authorization` across hosts
- [x] A redirect drops the original fragment when `Location` has none (RFC 9110, section 10.2.2: it is inherited)
- [x] 30,000 `100 Continue` responses are skipped without a bound
- [x] `format_request` writes two `Host` fields, or a `Content-Length` that disagrees with the body, when the caller set them (`hclient2.my`, `fmt.my`)
- [x] The server ignores `Content-Length: zz` when `Transfer-Encoding: chunked` is present (200, connection closed)
- [x] Body sizes are `int`: a `Content-Length` of 3000000000 is 413 and `BodyTooLarge` even with the limit at 2147483647. Document it, or count in `int64`
- [x] An older leak: a program that starts a server and a client 12,000 times grows 555 bytes a round on one worker (`manyserve3.my`). Not std.http's: every call of an actor's method from outside leaks 8 bytes natively, and a server makes one per worker when it stops (64 by default) and two per request with a limit. Filed as [[MYLA-576]] (the runtime's or the lowering's), left open here until it is fixed. Fixed there (a worker's ready queue walked along its 8 MiB ring): 568 kB at round 10 and 572 kB at round 11,999, where it was 7,224 kB

## What changed

**A request begun waits parked (B7).** `Link.read_request` no longer waits: it reads what the socket has, and when the request isn't all there it gives its `Reading` back (the parser, which part is coming, the time limit's start and end). `serve_ready` then keeps the reading and the bytes not taken yet in the server's `Pending` actor (by the connection's handle) and parks the connection on the lot with the tag `BEGUN` (-2) and the request's `read_ms` end as its deadline; the worker goes on with the next socket. The worker that takes the connection up when more comes (`__sock_tag(h) == BEGUN`) takes the reading back and goes on where it stopped, the connection's time's end with it. This holds for the head and for the body: a worker is held only while a request is complete and handled, or while bytes are there to read. The keeper answers 408 (as far as the socket takes it at once) and closes a parked request whose time ran out, and looks every quarter of `read_ms` too (`poll_ms`); one that gets bytes after its time is answered 408 by its worker, as before. An eviction past `max_connections` forgets its request. `Link.fill_until`, the `task.timeout` around a read, is gone. A request that comes whole costs what it did: no actor call, no new allocation but the `Reading` around its parser.

**The client.** A redirect to another host drops `Proxy-Authorization` with `Authorization` and `Cookie`; a `Location` without a fragment inherits the request's. The heads of informational responses count against the response's head limit (`after_informational`), so 30,000 `100 Continue` are `HeadersTooLarge`. Every request written (`format_request`, `Client`) has the body's framing and one `Host`: a caller's `Content-Length` is replaced by the body's (left out beside chunked, and when there is no body to frame), two `Host` fields or one that isn't a host and port are `BadHeader`, a transfer coding other than chunked is `Unsupported`.

**The parser.** A request's `Content-Length` beside `Transfer-Encoding` must still be a length (`content_length`, shared with the plain case): `zz` or `1, 2` is `BadLength` (400), past the largest `int` `BodyTooLarge` (413); a response's stays ignored, as before. Body sizes stay `int`s, documented: a body is a `str`, so it can't be longer than 2,147,483,647 bytes whatever the limit.

## Proposals (open decisions)

1. **Park a request begun with its parser, head and body alike** (the task's first option, extended to bodies), the parser kept in an actor of the server's by handle, the socket's tag saying it has one. Alternatives: park only incomplete heads and hold a worker for a body (a body dribbler, `Content-Length: 10` and one byte, would still hold one for `read_ms` each 16 KiB); cap the workers partial requests may hold (the task's second option: a bound, but past it the partial ones must wait or be closed, and the cap's workers are still lost to dribblers); keep the state in the runtime beside the parked socket (a value slot in a lot, a new primitive and a change to `lib/std/rt.my` and the interpreter: the tag is a number). Recommended: as built. It extends D190 (parked connections hold no worker) to connections whose request has begun; D190's "`read_ms` and `write_ms` apply only while a read or write waits" now reads: `read_ms` bounds a request's arrival whether it waits parked or not.
2. **`read_ms` of a parked request is kept by the keeper's look**, to within a quarter of the shortest of `idle_ms`, `keep_alive_ms` and `read_ms` (at most a second; 20 s by default is kept to within 1 s), and exactly when bytes come after it. Alternative: a timer per parked request in the runtime. Recommended: as built (as D190 did for `idle_ms`).
3. **The keeper's 408 is sent without waiting**: what the socket takes at once (the answer is about 100 bytes), then the connection is closed. Recommended.
4. **1xx responses are bounded by the head limit**, not by a count: their heads and the final head share `max_header_bytes` (64 KiB by default, about 2,600 `100 Continue`). Alternative: a fixed count of informational responses. Recommended: as built, as the limit already exists and a count would be a new constant.
5. **A request's framing is always the body's.** The caller's `Content-Length` is replaced (as `format_response` already does for a response); a non-chunked transfer coding is `Unsupported`. Alternative: refuse a caller's `Content-Length` that disagrees (`BadLength`) and keep one that agrees. Recommended: as built, the same rule as the server's responses.
6. **A request with both `Content-Length` and chunked is still read by the chunks** (and its connection closed after), its length checked to be one. Alternative: refuse every request with both (RFC 9112, section 6.1 allows it; it would change the pinned "chunked wins" behaviour). Recommended: as built.
7. **Body sizes as `int`**: documented, not counted in `int64`, as a body is a `str`. Recommended.
