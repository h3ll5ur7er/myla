Step 2 of the project tool ([[MYLA-64]]): parse `myla.toml` and `myla.lock`, the TOML subset of D73 whose grammar is on [[Architecture/Project-tool]], into a value, as `std.json` does for JSON ([[MYLA-79]]).

## Plan

- [ ] `std.toml` in Myla: `enum Toml { Str(str), Int(int64), Bool(bool), Array([Toml]), Table([(str, Toml)]) }` (tables keep their order), `parse(text) -> Result<Toml, TomlError>`, `struct TomlError { msg: str, line: int32, col: int32 }` (columns count characters, from 1), and lookups (`get(t, key)`, a dotted path)
- [ ] The subset exactly: tables and dotted headers, bare and quoted keys, basic and literal strings with TOML's escapes, decimal int64 integers with `_`, booleans, string arrays over several lines with comments and a trailing comma, inline tables; the table rules (a key once, a header once, `[a]` after `[a.b]`, inline tables closed)
- [ ] Everything outside the subset rejected with a message naming it: floats, `inf`/`nan`, dates and times, hex/octal/binary integers, multi-line strings, dotted keys, arrays of tables, arrays of non-strings
- [ ] Tests against Python's `tomllib`, as `tests/burn/test_json.py` tests `std.json` against `json`: a Myla driver parses length-framed documents from stdin and prints a canonical form; on a corpus of valid documents (hand-written and generated) the output equals the canonical form of `tomllib.loads`; on invalid documents (generated by mutation, and hand-written) `std.toml` fails exactly where `tomllib` fails, and on valid TOML outside the subset it fails with the "not supported" message; positions checked on hand-written cases
- [ ] Both native builds and both interpreters agree on a small corpus
- [ ] [[Language/Standard-library]] documents it
