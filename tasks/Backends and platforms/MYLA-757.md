A step of [[MYLA-165]], the Windows target (wave 6). `selfhost/target.my` says `debug_info: false` for x86_64-windows, so `-g` is refused there ("D216: debug information later"). [[MYLA-160]]'s plan for it: "on Windows DWARF first (gdb, lldb), CodeView/PDB for the Microsoft debuggers later (the PDB container is the expensive part)". Linux's hand-written DWARF is [[selfhost/dwarf.my]] (D82), with the gdb script `-g` embeds.

- [x] `myla build -g --target x86_64-windows` gives an `.exe` whose DWARF (in COFF sections, as clang and lld-link carry it) names Myla's source lines, functions and variables as Linux's does
- [x] A test under Wine (or with `llvm-dwarfdump`/`llvm-objdump` on the `.exe`) that a function's address maps to its `.my` line, and that a build without `-g` is byte-identical to today's
- [x] On the Windows runner (`scripts/windows-runner.py`): a case that checks the same with the image's LLVM tools, if they read it there (built, and run here on the same `.exe` with Linux's LLVM; whether the image's LLVM has `llvm-symbolizer` and `llvm-dwarfdump` shows CI's first run: a missing one skips its case and says so)
- [x] CodeView/PDB: a proposal (cost, what it gives Visual Studio and WinDbg users), not built (proposal 3; [[MYLA-777]] holds the work if it is taken)

## What COFF needs from the assembly

The DWARF is the same as Linux's, written by the same code ([[selfhost/dwarf.my]], the `dbg_*` methods of [[selfhost/codegen.my]]); clang assembles it into the COFF object as it does `.file` and `.loc`'s line table. Three things are written differently, all under `CodeGen.windows`:

- **The sections**: `.section .debug_info,"dr"` (discardable, readable), where ELF has `"",@progbits` (`dwarf.debug_section`). COFF's section names have 8 bytes, so clang puts `.debug_info` and the others in the object's string table (`/4`, …); lld-link keeps that table, and the names, in the image.
- **Offsets into another debug section** (the unit's `DW_AT_stmt_list` and its abbreviation offset): `.secrel32 .Ldebug_line0`, section-relative. `.long .Ldebug_line0` is right on ELF only because a debug section starts at 0 there; on COFF it would be the label's address in the image (`dwarf.section_offset`). References inside `.debug_info` (`.long .Ldty3 - .Ldebug_info0`) are differences and stay.
- **A code range's end** (`DW_AT_high_pc` of the unit, each function and each lexical block): its address (`DW_FORM_addr`, `.quad .Ldf12`), where Linux writes its distance from the start (`DW_FORM_data8`, `.quad .Ldf12 - myla_add`); the abbreviation table says so (`abbrev_section(coff)`, `dwarf.pc_range`). Not for correctness: clang works such a distance out itself, and for the 17,194 of `selfhost/main.my`'s that took it 31 to 59 s of assembling against 2.5 to 6.5 s with the addresses and 2.1 to 3.6 s without `-g` (2026-11-16, this branch on 478d656, clang 18.1.3, alternated twice on the shared machine at load 7 to 17). GNU `as` takes either in 1.2 s, so Linux keeps its form.

The addresses (`DW_AT_low_pc`, `.quad myla_add`) are the image's (`IMAGE_REL_AMD64_ADDR64`), as DWARF in a PE file has them; lld-link adds no base relocations for the debug sections (`.reloc` is the same size with and without them).

**The link** ([[selfhost/target.my]]'s new `debug_link`, the words the link ends with under `-g`; `build_commands(…, debug)` in [[selfhost/driver.my]]): `lld-link … /debug:dwarf /opt:ref`. Without `/debug:dwarf` lld-link drops every `.debug_*` section; with it no PDB is written, the COFF symbol table stays (gdb's and lldb's function names), and an empty CodeView entry is put in the debug directory. `/debug` turns lld-link's `/opt:ref` off, which then kept the import libraries' unused thunks (`.text` 0x55a6 against 0x5405 bytes for a small program); `/opt:ref` keeps `.text` byte for byte the object's, as without `-g`. Linux's linkers keep DWARF anyway (`debug_link` is `[]` there).

**The gdb script section** (D82) applies on Windows: `.debug_gdb_scripts` is a debug section like the others (`"dr"`), and gdb reads it from a PE file as from an ELF one (`info auto-load python-scripts` lists `myla-printers`; under Wine the printers show `xs = [Point {x: 2, y: 3}, …]`). lldb ignores it, as on Linux.

## What gdb, lldb and LLVM's tools show

For [[tests/burn/test_debug_info.py]]'s `WIN_PROGRAM` (`add` at line 6, `main` at 11), built on Linux:
- `llvm-symbolizer --obj=prog.exe 0x140004693` (`myla_add`'s low_pc): `myla_add`, `…/main.my:6:1`; `llvm-dwarfdump --lookup` gives the same line; `--verify`: `No errors.` (the warnings it prints, a subprogram with `DW_CHILDREN_yes` and none, are Linux's too).
- gdb (Linux's, from the file): `info line myla_add` is line 6, `break main.my:7` is `file main.my, line 7`, `info scope myla_add` names `a` and `b` at `$rbp` offsets, `info functions` has `fn myla_add(int32, int32) -> int32`.
- lldb 18: `image lookup -n myla_add -v` is `myla_add at main.my:6:1` with its variables and types, `breakpoint set -f main.my -l 7` resolves.
- **gdb on the running program under Wine** (`winedbg --gdb prog.exe`, which runs `gdb` attached to its proxy): it stops at `main.my:7` in `myla_add (a=2, b=3)`, `bt` has `myla_main () at main.my:15` and `_start`, `info locals` one frame up shows `p = Point {x: 2, y: 3}`, `name = "two"` and the list through the printers, and `finish` says `Value returned is $1 = 5` (4.7 s).

## Proposals (accepted 2026-11-17: the first is D247, the second D248, the third stands as written: CodeView later, MYLA-777)

1. **Debug information on Windows is DWARF in the `.exe`** (built). Proposed row: *"`myla build -g --target x86_64-windows` writes Linux's DWARF into the COFF object, with COFF's section flags (`"dr"`), section-relative offsets (`.secrel32`) and an absolute `DW_AT_high_pc`, and the pretty-printers' `.debug_gdb_scripts` ([[MYLA-757]]); `lld-link /debug:dwarf /opt:ref` keeps it in the image, without a PDB and with the code as without `-g`. gdb and lldb read it on Windows, gdb under Wine too; the Microsoft debuggers don't (no CodeView). Changes D216's 'No debug information at first' for Windows."* Alternatives: CodeView and a PDB first (proposal 3: more work, and of no use to gdb, lldb or the VS Code adapter, D78); DWARF in a separate file (`/debug:dwarf` and an `objcopy --only-keep-debug`-like split; Windows has no `.gnu_debuglink` convention that lld-link writes, and nothing else needs the split yet).
2. **`DW_AT_high_pc` is an address on COFF and a length on ELF** (built): the abbreviation table differs by target in that one form. Alternatives: the address everywhere (the same table for both, but Linux's `-g` output and the table recorded from the Python backend change, for nothing GNU `as` needs); the length everywhere (one table, a `-g` build of a large program 5 to 10 times slower to assemble on Windows).
3. **CodeView/PDB: later, as CodeView records the code generator writes and a PDB lld-link builds** (not built; [[MYLA-777]], backlog). *What it gives*: Visual Studio's and WinDbg's (and cdb's) source breakpoints, stepping, call stacks with lines, locals, watch and hover, symbolized crash dumps (WER minidumps) and profiles (ETW, WPA, VTune): what a Windows developer without gdb or lldb expects; today they see addresses only. *Its cost*: (a) the line table through clang's CodeView directives (`.cv_file`, `.cv_func_id`, `.cv_loc`, `.cv_linetable`, `.cv_filechecksums`, `.cv_stringtable`), small, as `.loc` is; (b) the symbols (`S_GPROC32_ID`, `S_FRAMEPROC`, `S_REGREL32` for `%rbp`-relative slots, `S_BLOCK32`, with `.secrel32`/`.secidx` relocations) and types (`LF_STRUCTURE`/`LF_FIELDLIST`, `LF_POINTER`, `LF_ARRAY`, `LF_PROCEDURE`, enums as a union with a tag, as Rust's MSVC target does) written as data, about as much as today's `dbg_*` methods (395 lines) and `dwarf.my` (280); (c) what CodeView can't say: a `str` as two computed pieces, a list's length read from its cell, a variable in an async function's heap frame through `%r15` (DWARF expressions, D75, MYLA-141) have no CodeView form, so they come as pointers to their cells and a `.natvis` file shows them (the gdb printers' part, about their 180 lines in natvis's XML, embedded with lld-link's `/natvis`); (d) the PDB itself, the "expensive part" of [[MYLA-160]], is lld-link's: `/debug:full` builds it from the objects' `.debug$S`/`.debug$T` and still keeps the DWARF sections beside it (tried with lld 18 on a C object carrying both: the `.exe` has the four `.debug_*` sections and a `.pdb` is written). A PDB writer of our own (the MSF container, the DBI, TPI, IPI and symbol-record streams, their hash tables) is needed only if Myla writes its PE files itself one day (D211's later step): several thousand lines, as LLVM's. *Before it*: unwind tables ([[MYLA-776]]), without which those debuggers' stack walks stop at the first Myla frame. *Tests*: `llvm-pdbutil dump` and lldb's PDB reader on Linux; cdb on the runner if the image has the SDK's debuggers. Alternatives: DWARF only, for good (the Microsoft debuggers never see Myla's lines; VS Code works through the adapter with a Windows gdb); converting the DWARF afterwards (`cv2pdb`, which runs on Windows only and needs Visual Studio's `mspdbcore.dll`: nothing for the code generator, but not on Linux's CI and not reproducible); our own PDB writer now (the most work, for nothing lld-link doesn't do). Proposed row, if taken: *"The Microsoft debuggers get CodeView ([[MYLA-777]]) after the unwind tables ([[MYLA-776]]): the code generator writes CodeView records beside the DWARF, lld-link builds the PDB (`/debug:full`), a natvis file shows the cells; no PDB writer of Myla's own while lld-link links."*

## Found
