## What MYLA-702 couldn't check under Wine

- A read of the standard input with a time limit (`Reader.ready(ms)`, std.platform's `poll_read`) asks a pipe how much it holds (`PeekNamedPipe`) until the limit. Under Wine the pipe a Linux parent hands over isn't a named pipe, so the call fails and the read is taken for ready (it then blocks): the limit is to be checked on the runner.
- A frame larger than a page ([[MYLA-717]]): Wine maps the whole stack. `tests/burn/test_windows.py`'s `FramesOnWindows` (a recursion through a 64 KiB frame on the main thread and a worker) was skipped under Wine and meant to run where `sys.platform` is `win32`, where `CAN_BUILD_NATIVE` (x86-64 Linux) skipped it too: it ran nowhere. Its program is now `FRAMES`, run under Wine by `FramesOnWindows` and on Windows by the runner's `frames/64-kib`.

## What MYLA-707 couldn't check under Wine

[[MYLA-707]]'s console cases for this job are `RUNNER_CASES` in [[tests/burn/test_windows.py]]: each runs that file's `CONSOLE` program, built for Windows as `console.exe`, in a console of its own (`CREATE_NEW_CONSOLE`), its input that console and its output a file, as `cmd /c "console.exe ARGS > out.txt"` gives; the driver attaches to the console (`AttachConsole`, after `SetConsoleCtrlHandler(NULL, TRUE)` so that its own events don't end it), types keys into it (`WriteConsoleInputW` on `CONIN$`), sends `GenerateConsoleCtrlEvent(event, 0)` or closes the console's window (`WM_CLOSE` to `GetConsoleWindow()`), and compares the output file and the exit status. If `cmd` itself ends on a console's event, the driver starts `console.exe` with `STARTF_USESTDHANDLES` instead: `CONIN$` its input, the file its output, the console's `CONOUT$` its error. The cases, each a program's arguments, its steps, and what it must print and exit with:

| --- | --- | --- | --- | --- |

| The window's size | `size`, after `mode con: cols=101 lines=33` | — | `stdin 101 33`, `stdout none`, `stderr 101 33` | 0 |

| The console closed (Terminate, then the program's own exit within 5 s) | `close closed.txt`, `console.exe` alone | after `closed.txt` says `ready`: `WM_CLOSE` | `closed.txt`: `ready`, `got terminate` | 7, within 10 s |

They are wired: `scripts/windows-runner.py build` makes each a case `terminal/NN-…` from `RUNNER_CASES` itself (the one source; a new case goes there), `run` drives it on Windows (`drive_console`, the driver a process of the script's own per action, `console-action`, with ctypes: attached to the case's console, its own events handled so none ends it) and skips all ten under `--wine` with the reason. The fallback above (`STARTF_USESTDHANDLES` if `cmd` ends on an event) isn't needed: on the first run `cmd` passed the program's status on through Ctrl-C and Ctrl-Break (04, 05).

The window's size and a real Ctrl-C are what Wine can't give at all; under Wine `Console` checks the rest with a pseudo-terminal as the console and a Unix SIGINT as Ctrl-C, but not virtual-terminal input, a Ctrl-Break, a close, `STATUS_CONTROL_C_EXIT` (Wine's default ends with 0) or a read a Ctrl-C ends.

## The first run on windows-latest (run 43800131972, job 133078480047)

155 of 160 cases passed on Windows, among them the stack probes, sockets, the standard input's time limit and `tools/myla-build` with the image's LLVM 20.1.8; `terminal/01` to `05` passed, `06` to `10` failed. The causes, and what changed (`scripts/windows-runner.py`, `RUNNER_CASES`):

- **08, 09, 10 ended at once with exit 1 and nothing written: the driver named the program `console.exe`.** `cmd /c "console.exe ctrl raw token > out.txt"` hands the program that bare name as its `argv[0]` (cmd finds it in its directory), and `ctrl` and `ends` start `process.args()[0]` again as a child, which std.process looks for on PATH only (D225): `runtime error: spawn: program not found` on the console's stderr, which no file kept. Under Wine the same command line gives the same (`wine cmd /c "console.exe ends > out.txt"`: that error, exit 1), and with the program named by its path both run (`.\console.exe` and `Z:\…\console.exe`: exit 0, the nine lines). The driver now names console.exe by its whole path (`console_command`), as a program that starts itself needs on Windows; `tests/burn/test_windows_runner.py` holds every case's command to it. Not the program's fault: D225 is the rule, and `args()[0]` is what the parent wrote.
- **06 waited for "caught interrupt" for good: a Ctrl-C written with `WriteConsoleInputW` is no Ctrl-C.** conhost's `WriteConsoleInputW` puts the records into the input buffer as they are (`InputBuffer::Write`, microsoft/terminal's `src/host/inputBuffer.cpp`: only Ctrl-S is looked at there); the Ctrl-C handling, the cooked read ended with `ERROR_OPERATION_ABORTED` and `CTRL_C_EVENT` sent, is for keys typed at the console (`HandleGenericKeyEvent`), and for a terminal's ETX on a pseudo console. So the case now runs on a pseudo console (`"host": "pty"`: `Pty`, CreatePseudoConsole and `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`), its keys typed as a terminal types them (`vt_input`: Ctrl-c is ETX); cmd gives the program the console's own input and error (`< CON`, `2> CON`), whatever the runner's are. What the program does with a real Ctrl-C during a console read is what `Console.test_a_read_of_the_console_while_a_listener_takes_a_ctrl_c` shows under Wine (it passes).
- **06 left its console.exe running, which the job's cleanup killed with its conhost**: the driver killed only `cmd`. It now ends a console case's whole tree (`taskkill /F /T`), then any `console.exe` left, whatever the case did (`end_console_case`), and a failure of the driver itself fails its case instead of the run.
- **07 ran on for 10 s after `WM_CLOSE` to `GetConsoleWindow()`'s window, with nothing to show why.** A close that reached the program ends it within Windows' 5 seconds either way (its own exit, or the system's after the handler's time), so the close didn't reach it; a NULL window, whose message goes to the sender's own queue and is "posted" all the same, would explain it, but the log can't tell. The case now closes a pseudo console (`ClosePseudoConsole`, which is `CTRL_CLOSE_EVENT` to its processes, no window needed); the classic close says "the console has no window" when there is none.
- **A failure says what the case wrote**: out.txt or the case's file, and the console's text (a classic console's screen read by `console-action screen`, a pseudo console's output with its escape sequences left out), so that a runtime error on the console's stderr is in the log.

## The second run (run 43803052380, job 133087772948, `29cfb8a`)

159 of 160: 07 to 10 passed. `terminal/06-readline` wrote `ready`, `end`, `caught interrupt`: the pseudo console's ETX was a real Ctrl-C, but the read of the console's lines it ended gave 0 bytes and no error, which std.platform's `read` took for the end (it went on only after `ERROR_OPERATION_ABORTED`). The platform module's fault, fixed there: the console's control handler counts the Ctrl-Cs and Ctrl-Breaks, and `read` goes on after such a read when the count moved, waiting up to 100 ms for it ([[MYLA-707]]'s "Fixed after the runner's run" has the details and the tests). Wine doesn't end the read at all, so only the runner's 06 shows the read itself.

## What only the Windows runner shows

None of this has run on Windows yet: the pull request's run of the `windows` job is the first.

- `frames/64-kib`: a frame past the guard page faults on Windows without [[MYLA-717]]'s probes, on the main thread (`/stack`) and on `CreateThread`'s stacks; Wine commits the whole stack.
- `stdin/ready`: `PeekNamedPipe` on the pipe Python gives a child (Windows' anonymous pipes are named pipes); under Wine only the Windows parent's (`stdin/ready-from-a-child`) shows it.
- `tools/myla-build`: `myla.exe` running clang, llvm-dlltool and lld-link on Windows (D211) and `myla.exe test --native`; under Wine the tools are Linux programs a Windows program can't wait for, so the case is skipped there. `windows-latest` is Windows Server 2025 (image 20261111.331.1) with LLVM 20.1.8 in `C:\Program Files\LLVM\bin` (its README); LLVM's Windows installer installs the toolchain tools, which include `llvm-dlltool` (`LLVM_TOOLCHAIN_TOOLS`, AddLLVM.cmake) and lld's `lld-link`, so the case should run there: the script names each tool's path and version first.
- `terminal/06-readline` and `07-close` on a pseudo console (`Pty`): ConPTY from Python's ctypes has run nowhere yet (Wine has no Windows Python here, and running one under Wine was refused in this session); only the records' layouts (STARTUPINFOEXW 112 bytes, its attribute list at 104; PROCESS_INFORMATION 24; COORD 4) and the typed bytes are checked here. If 06 fails again, the report now carries the pseudo console's text; if 07 does, `closed.txt` tells a close that didn't reach the program (`ready` alone) from a program that didn't end (`got terminate` too).
- `terminal/…` (all ten, [[MYLA-707]]): raw keys and virtual-terminal input from a real console, UTF-8 typed into a cooked read, the window's size, real Ctrl-C and Ctrl-Break events (`STATUS_CONTROL_C_EXIT`), a Ctrl-C ending a console read, the console closed, D192 and D187 on Windows' console; and the driver itself (`AttachConsole`, `WriteConsoleInputW`'s records, `GenerateConsoleCtrlEvent`, `WM_CLOSE`), which nothing here can run: only its key records' encoding is checked here (`INPUT_RECORD` 20 bytes, the event at 4; each `RUNNER_CASES` key name encodes).
- `console/random` on Windows' own `BCryptGenRandom` and `%TEMP%`.
- Windows' own `CreateProcessW`, `cmd`, PATH and PATHEXT, `TerminateProcess` and 400 children at once; the console's and the C runtime's splitting of a command line Python wrote (`list2cmdline`); a stack overflow's exception on a real guard page; `WaitOnAddress` and the workers on the runner's processors; a drive letter for the working directory.

## Proposals (accepted 2026-11-16: D233, D234 and D235)

1. **The Windows tools are published by the `windows` job, after its run passed** (built): `myla-x86_64-windows-<sha>`, a zip of `myla.exe` and `myla-lsp.exe` (an artifact's own; no tarball, as no executable bit is to be kept). Alternatives: from `windows-build`, as soon as they are built (as `bootstrap` publishes what it built and checked on its machine, but nothing would have run them), or a tarball as the Linux tools are. Proposed row: *"CI publishes each master commit's `myla.exe` and `myla-lsp.exe` as the artifact `myla-x86_64-windows-<sha>` (90 days) from the `windows` job, once they ran there: built on Linux by `windows-build` with the programs it runs (D207, D213, D214, [[MYLA-708]])."*
2. **A missing LLVM tool on the runner skips `tools/myla-build` with an annotation** (built), as the task asked, rather than failing the job as `MYLA_REQUIRE_TARGETS` fails the Linux ones. Alternative: fail, since the image ships them (a later image without one would then turn the job red instead of yellow).
3. **The stress programs 3 times on each worker count on Windows** (built, `--runs 3`), against bootstrap-arm64's 20: Windows' memory order is x86-64's, which the burn job's own runs cover; what is Windows' here is the threads, the parking and the poller. Alternative: 20, at about seven times the stress cases' share of the job.
