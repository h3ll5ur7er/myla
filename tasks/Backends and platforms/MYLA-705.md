A step of [[MYLA-165]], the Windows target, in the plan the owner accepted on 2026-11-14 ([[Project/Follow-up-plan#windows-2026-11-14]]). `CreateProcessW` with a quoted command line, pipes for the standard streams, the program found through `PATH` and `PATHEXT` ([[MYLA-190]]); the exit code with 32 bits (D216).

- [x] std.process: `run`, `command`, pipes, waiting, killing
- [x] test_process passes under Wine; the exit code's 32 bits documented on [[Language/Targets]]
- [x] The record's `spawns: true` (D217): a test harness's cases run as children on Windows ([[MYLA-370]])

## What changed

**Starting a child** ([[lib/std/platform_windows.my]], "processes"). `spawn_piped`, `spawn_with`, `run_with` and `run` start the child with `CreateProcessW`:
- *The program* is looked for by the platform itself (std.rt's `program_paths` hands the name over as it is on Windows): `program_candidates` gives a name with a directory (a `/`, a `\` or a drive) as itself and then with each of `PATHEXT`'s extensions, a name alone the same in each of `PATH`'s `;`-separated entries (quotes taken off, empty ones skipped), itself first only when it has an extension. Each candidate is tried in turn, as `execvp` tries PATH's on Linux: one not there (or not a program: ERROR_BAD_EXE_FORMAT) gives way to the next, one that may not be run is remembered (`PermissionDenied` if none starts), a file that isn't a program is ENOEXEC's `Other(8)`.
- *The arguments* are one command line (`command_line`), the inverse of the splitting [[MYLA-702]] wrote for `args()` (`splits_back` holds the two to each other): the program's name between quotes (a quote in it is `InvalidInput`), an argument quoted when it is empty or has a blank, a quote inside after its backslashes doubled and one more, the backslashes before a closing quote doubled.
- *A batch file* (`.bat`, `.cmd`, which CreateProcess would hand to cmd with arguments it doesn't quote for cmd) is run as `cmd.exe /e:ON /v:OFF /d /c ""script" args"` with each argument quoted for cmd as Rust quotes it since CVE-2024-24576 (`bat_command_line`: quotes unless only letters, digits and `#$*+-./:?@\_`, a quote doubled, `%` written `%%cd:~,%`); a carriage return or a newline in one is `InvalidInput`, and only a batch file that is there is tried.
- *The streams* (`child_streams`) as `stdio_mode`'s letters, as on Linux: `p` an anonymous pipe (64 KiB asked), `i` a copy of this process's handle, `n` the `NUL` device, and for the input `t` a text in a temporary file deleted on close (`input_file`, what Linux's `memfd` is; an empty text is `NUL`) or `d` a copy of the descriptor handed over, closed once the child has it. The child's three are `STARTUPINFO`'s and the only handles it inherits (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, `STARTUPINFOEXW`; this process's ends are never inheritable).
- *The directory* is checked first (`GetFileAttributesW`), so a bad one is `WorkingDir(2)` or `WorkingDir(20)`, not the program's error; *the environment* given is built from this process's (names compared without their case, as Windows compares them) and sorted by name, as `CreateProcessW` wants a block.
- `CreateProcessW` has ten arguments, `DuplicateHandle`, `CreateFileW` and `UpdateProcThreadAttribute` seven: they go through the runtime's new `__win_call` ([[selfhost/runtime_x86.my]], `emit_windows_calls`), called as `__syscall(__rt_addr("__win_call"), block, 0, 0)` with the function and its ten words in a block (`win_call`). No primitive, so no `Stage:` commit.

**Waiting and killing.** The child's process ID is its `pid`; its process handle is the descriptor `exited`, ready once it ended for `poll_read` (`WaitForSingleObject`) and the poller, and while it is open it keeps the ID the child's, so `reap`, `try_reap` and `kill` open the child again by ID (`OpenProcess`). `kill` is `TerminateProcess` with the exit code 1 (Windows has no signals; see the proposal), nothing for a child that ended already. `run_with` reads both pipes as either has bytes (`PeekNamedPipe`, a millisecond's nap while neither has), the last one left with plain reads, then waits for the process: `__run_exit_code` is its exit code's 32 bits. A descriptor past 2 is a handle itself (`std_handle`), so `read`, `write`, `close` and `poll_read` take a child's pipes; `close` sets no standard handle for one.

**The exit code's 32 bits** (D216). `__reap` and `__try_reap` give an int32 in which a negative number is a signal and 256 "still running": a Windows code such as 256, 70000 or 0xFFFFFFFE would read as either. std.rt's `reap` and `try_reap` now record the platform's whole status as a run's (`reaped`: `__set_run_status`, the words `__run_exit_code` and `__run_signal` read, each worker's own) and give its low 8 bits, and std.process's `Child` and `run_async` read the status there (`reaped_status`, which replaces `status_of`). On Linux every status is what it was. `run_async` reaps the child before it closes `exited` (on Windows the handle that keeps the ID the child's).

**The poller** ([[lib/std/platform_windows.my]], "the poller"). What MYLA-702's waited only for timers now watches what processes need: a pipe until it holds bytes or its writer closed it, and a process until it ended. Its block holds the watches (each armed once, as EPOLLONESHOT's), the last wait's events and a wake-up event (`poller_wake` sets it). A wait looks at each armed watch, then waits in `WaitForMultipleObjects` for the processes and the wake-up event, a millisecond at a time while a pipe is watched (an anonymous pipe can't be waited for). Anything else (the console, a file) can't be watched and is ready at once, as a regular file is on Linux. Left for [[MYLA-706]]: the I/O completion port (pipes as overlapped named pipes, no millisecond's polling), sockets, and the room in a pipe for a write ([[MYLA-726]]).

**The poller with workers** (the merge of [[MYLA-703]] and [[MYLA-704]], `b08325c`). With threads, one worker waits in the poller (std.rt's `__exec_polling`) while any other watches, forgets (under std.rt's watch lock only) or wakes; the first block, without a lock, broke there: a grow in `poller_watch` freed the arrays a wait was reading. Now the block has a spin lock of its own (`poller_lock`, `__xchg64`; held for a few loads and stores, never across a system call), and a wait works on a copy: under the lock it copies the armed watches (descriptor, token, kind, handle) and counts itself waiting; without it, it looks at them and waits (`WaitForMultipleObjects` on the copy's processes and the wake-up event); under it again it records an event only for a watch still there, armed and with the same token (a stale one is dropped), and counts its wait over (`waits`). `poller_watch` wakes a wait going on, so a new process is waited for at once; `poller_forget` wakes it and returns only once that wait is over, so std.rt, which forgets a watch whose last waiter went before it closes the handle (`watch_unlink`), never closes a handle a wait holds (a wait on a closed or reused handle is undefined on Windows). A handle closed while frames still wait on it (`watches_closed`) isn't forgotten first: the wait's check drops its event, and the wait holds the object until it returns; [[MYLA-706]]'s completion port ends that case. The events and the copy are the waiting worker's own. The event-based wake-up replaces Runtime's poller word (`WaitOnAddress`) for the poller; `park` and `unpark_one` stay Runtime's.

**Children of a harness** ([[selfhost/target.my]], [[selfhost/driver.my]]). The Windows record's `spawns` is true: `myla test --target x86_64-windows` runs the harness once under Wine and the harness starts a child of itself for each case; Wine starts a Windows program's children itself, so the driver gives the harness no emulator for them (`MYLA_TEST_EMULATOR`, which qemu-user needs).

**Tests.** [[tests/burn/test_windows.py]]'s `Children` (new): a Windows helper program (`HELPER`) as the child of `CHILDREN`, which runs std.process through each of the above, and `myla test --target x86_64-windows` on cases that pass, fail, expect a panic and an `exit`, one of them reading its scratch directory `c6` (a child's; runs of the harness have one for all). ## Proposals (accepted 2026-11-15: the first is D224, the second D225, the sixth D226, the others stand as built, D227)

1. **`kill` on Windows ends a child with the exit code 1** (built), as Rust's, Python's and Go's `kill` do: `wait` then gives `Exited(1)`, and `Signaled` never comes on Windows. Alternatives: the code 137 (128 + 9, what a shell shows for a SIGKILL), or `Signaled(9)` from a `Child` that remembers it killed the child (a status Windows never reported, and `run_async`'s cancel would need it too). Proposed row: *"On Windows `kill` ends a child with `TerminateProcess` and the exit code 1, as Rust's and Python's do; a child's status is always `Exited` with the code's 32 bits (D216, [[MYLA-705]])."*
2. **Windows looks for a program on PATH only, with PATHEXT** (built): a name alone in each of PATH's entries with each of PATHEXT's extensions (itself first when it has one), a name with a directory as itself and then with the extensions; not this process's directory first (cmd's, and CreateProcess's search, which also looks in the program's and the system's directories and appends only `.exe`). It is D147's search, as on Linux, and Rust's since it stopped searching the working directory. Alternative: CreateProcess's own search (`lpApplicationName` NULL), which finds programs a Linux-minded reader wouldn't expect and can't take PATHEXT. Proposed row: *"On Windows a program named alone is looked for in each of `PATH`'s entries with each of `PATHEXT`'s extensions, not in the working directory first; one named with a directory is itself, then itself with the extensions (D147, [[MYLA-705]])."*
3. **A batch file is run by cmd with its arguments quoted for cmd** (built), Rust's quoting since CVE-2024-24576. Alternatives: refuse batch files (`InvalidInput`), or leave `.BAT` and `.CMD` out of the search (then `npm`, a `.cmd`, isn't found).
4. **A reaped child's whole status goes through the run's words** (built, `__set_run_status`), so no primitive changes its type. Alternative: `__reap` and `__try_reap` with `int64` results (the checker's, the interpreter's and both back ends' types, and a `Stage:` commit, as std.process is in the compiler).
5. **A relative program path is this process's directory's**, not the `cwd` given's (built: CreateProcess's, and Rust's on Windows); on Linux the child changes directory and then looks. Alternative: join it with the `cwd` given first.
6. **The poller's copy of a handle is the handle itself, not a `DuplicateHandle`** (built), with `poller_forget` waiting for the wait that copied it to end. A duplicate of a pipe's read end would keep the pipe open after the program closed it (a child's writes would not fail, and `run_async`'s child would not see its reader gone), it would outlive a watch std.rt closes without forgetting it, and it costs two calls a handle a wait. Alternative: duplicates owned by the poller, closed when the wait ends (no wait on the program's handles at all, at that cost). Proposed row: *"Windows' poller waits on the program's own handles under a lock of its own, never held across the wait; a watch forgotten wakes the wait and returns once it is over, so a handle is never closed while waited on ([[MYLA-705]], [[MYLA-703]])."*
