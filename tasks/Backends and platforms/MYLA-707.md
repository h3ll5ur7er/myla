## What was built

**The terminal** ([[lib/std/platform_windows.my]], "the terminal and signals"). A descriptor is a terminal when its handle has a console mode (`GetConsoleMode`): the console's input or one of its screen buffers. Its size is a screen buffer's window (`GetConsoleScreenBufferInfo`'s `srWindow`); the input has none of its own and gets that of the active screen buffer (`CONOUT$`), as Linux gives a terminal's size on each of its descriptors. The saved mode is the handle's console mode, 4 bytes. Raw mode is the input without `ENABLE_LINE_INPUT`, `ENABLE_ECHO_INPUT` and `ENABLE_PROCESSED_INPUT` (Ctrl-C a key, Enter a CR) and with `ENABLE_VIRTUAL_TERMINAL_INPUT` (a console that refuses it is set without); a key at a time (`cbreak_mode`) is the input without line input and, as Windows echoes only a line it edits, without echo (see the proposals). `term_enable_vt` sets `ENABLE_VIRTUAL_TERMINAL_PROCESSING` on a screen buffer, and leaves the input as it is (its mode's 4 is `ENABLE_ECHO_INPUT`): the first screen buffer it changes and its mode before are kept in `__win_console_cp`'s second half and put back at the exit with the code pages (`console_back`, from `exit`). std.term and std.rt are unchanged.

**The signals.** The console's control handler is the runtime's `__win_on_ctrl` ([[selfhost/runtime_x86.my]], `emit_windows_ctrl_handler`), which std.platform adds with `SetConsoleCtrlHandler` the first time a program listens or makes the console raw (`ctrl_handler_added`, under `__sig_pipe`'s lock) and never removes. Windows calls it on a thread it makes, which has no state block of the runtime's (D222's TLS slot is empty there), so it is assembly that reaches only the process's words, as Linux's `__on_signal` is: Ctrl-C and Ctrl-Break are 2, the console's close, a logoff and a shutdown 15. While someone listens (`__sig_pipe`'s count) it writes the byte to the signal pipe (`CreatePipe`, not inherited, made by the first listener; the byte and the count written on its own stack) and returns TRUE; after a 15 it waits first (`Sleep(INFINITE)`), since Windows ends the process once its handlers return, so a program has Windows' time (5 seconds for a close) to end itself, as Go's runtime does. Else, while the exit hook holds a raw mode, it calls `__on_raw_signal` (std.platform's `raw_signal`: the mode put back with `SetConsoleMode`, then the code pages and the output mode; it allocates nothing, inlined to loads, stores and `__syscall`s with no `%gs` operand) and returns FALSE, so that Windows' default handler ends the process (`STATUS_CONTROL_C_EXIT`; D192). Else it returns FALSE at once, as if it weren't there. It saves the registers Win64 keeps and Myla's code doesn't (%rdi, %rsi, %xmm6 to %xmm15). `signal_listen`, `signal_take`, `signal_fd` and `drain` are Linux's over the pipe (`ReadFile`, `PeekNamedPipe`); the reactor waits on the read end as on a child's pipe (D226's poller).

**A read of the console that a Ctrl-C ends** (`read`, `console_read_aborted`, `read_ended_by`, `ctrl_counted_since`): Windows ends a waiting read of the console's lines with nothing read when Ctrl-C (or Ctrl-Break) is typed, and no error: `ERROR_OPERATION_ABORTED` is what `ReadConsoleW` sets, not `ReadFile` (the fix below); the read then goes on, as Linux restarts a read a caught signal interrupts (`SA_RESTART`), and Python's console reader does the same. The error is cleared, so a later end of the input isn't taken for one. Wine doesn't end the read; the runner's case checks it.

## What Wine's console doesn't show

Wine 9.0's console, on a pseudo-terminal: it has no virtual-terminal input (an arrow, Delete or F5 is dropped, Alt-x comes as `x`, and Ctrl-C typed in raw mode ends the read with nothing, which std.term takes for the input's end), its screen buffer isn't the terminal's size when the output isn't the terminal (80 by 150 then), a Unix SIGINT is its only Ctrl-C (no Ctrl-Break, no close, logoff or shutdown; SIGTERM ends Wine itself), its default handler ends a program with 0, not `STATUS_CONTROL_C_EXIT`, and a cooked read isn't ended by a Ctrl-C. `RUNNER_CASES` in [[tests/burn/test_windows.py]] gives each as a run of `CONSOLE` on Windows' own console, with its steps and what it must print and exit with; [[MYLA-708]] lists them.

## Proposals (accepted 2026-11-16: the first and the fourth are D230, the second D231, the third D232)

1. **One control handler, added the first time it is needed and never removed** (built). It decides by the state (a listener, raw mode) what an event does, and passes it on when neither applies, which is what no handler does. Alternatives: add it with the first listener and remove it after the last (`Signal.md`'s plan before), with a second routine for raw mode: Windows calls the last added first, so raw mode's routine, added after a listener, would put the mode back and pass on a Ctrl-C the listener then takes, leaving the program running cooked; and a removal can race an event's thread already in the routine. Proposed row: *"Windows' console control handler is one routine of the runtime's (`__win_on_ctrl`), added the first time a program listens for signals or makes the console raw and never removed: while someone listens it writes the signal to std.signal's pipe and handles the event, after a close, a logoff or a shutdown waiting until the program ends itself or Windows' time runs out; else, while the console is raw, it puts the mode back and passes the event on to Windows' default; else it passes it on ([[MYLA-707]], D216, D192)."*
2. **A key at a time doesn't echo on Windows** (built). `SetConsoleMode` refuses `ENABLE_ECHO_INPUT` without `ENABLE_LINE_INPUT`, so `cbreak_mode` (what `myla repl` keeps while an input runs) clears both. Alternatives: echo in std.term (it reads nothing while a program runs: that is the point of the mode), or leave Windows' line input on (the 4,095-byte line limit `cbreak_mode` exists against has its Windows equivalent too). Proposed row: *"On Windows `cbreak_mode` takes keys one at a time without echo, as the console echoes only a line it edits ([[MYLA-707]])."*
3. **The output mode `enable_ansi` changed is put back at the exit, with the code pages** (built; MYLA-702's proposal 3 did it for the code pages). Alternatives: leave escape sequences on (Rust's crossterm and Python do; Windows Terminal has them on anyway). Proposed row: *"A Windows program puts back at its exit the console's output mode that `enable_ansi` changed, as it puts back the code pages ([[MYLA-707]], D215)."*
4. **A read of the console that a Ctrl-C ends with nothing read goes on** (built), as Linux's `SA_RESTART` and Python's console reader. Alternative: give the read's caller `Interrupted` (std.io's readers would have to retry). Part of row 1's text if accepted: *"…; a read of the console's lines that a Ctrl-C or a Ctrl-Break ends goes on (Windows gives it 0 bytes and no error; the console's control handler counts the events, and `read` waits up to 100 ms for the count, as Python does)."*

## Fixed after the runner's run (MYLA-708)

`terminal/06-readline` on windows-latest (run 43803052380, job 133087772948, `29cfb8a`): `out.txt` was `ready`, `end`, `caught interrupt`: the pseudo console's ETX was a real Ctrl-C (the listener caught it), but the read of the console's lines it ended gave 0 bytes and no error, and `read`, which went on only after `ERROR_OPERATION_ABORTED` (995), took it for the end. Now the console's control handler counts each Ctrl-C and Ctrl-Break before anything else (`__win_on_ctrl`: `lock incq` on `__win_console_cp`'s fifth word, which `codegen.my` grows from 32 bytes to 40; the handler runs on a thread without a state block, so a process word), `read` takes the count before `ReadFile`, and after a read of a console in line-input mode that gave nothing, it goes on when 995 is set (as `ReadConsoleW` sets it) or the count moved, waiting up to 100 ms for it (the handler's thread can come after the read returned; Python's console reader waits 100 ms for its SIGINT the same way); else it is the end, as Ctrl-Z at a line's start is. Every other read is as before (a read that gave bytes, a raw read, a file, a pipe: their error is kept for the caller's cause). Only Windows' code changed: `gen_main`, `maps` and `concurrency` of `29cfb8a`'s tree compiled by this compiler and by `29cfb8a`'s give byte-identical Linux, aarch64 and wasm32 assembly (the Windows assembly has the count), and the seeds bootstrap it (no `Stage:`).

Tests: `read_ended_by`'s five `#test` cases (no console, two raw reads, an abort, a read of lines that waits for the count; pure, so they run on every host as the module's other cases do) and `test_windows.ControlHandler` (`CTRL_COUNTED`, a case only Windows runs, appended to a copy of the library's module: a Ctrl-C to a console of the case's own, `AllocConsole`, while it listens, counted once and SIGINT written after), which fails, `(0, 2)`, with the compiler built without the handler's count. Wine can't show the read itself: under Wine 9.0 a Ctrl-C doesn't end a waiting read of the console at all (`Console.test_a_read_of_the_console_while_a_listener_takes_a_ctrl_c` passes with `console_read_aborted` never going on), and a Ctrl-Z there is read as a character (`\x1a\r`), not the end; the runner's `terminal/06-readline` is the case of it.
