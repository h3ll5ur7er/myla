Found by [[MYLA-705]]. The `#test` cases of [[lib/std/process.my]] start `cat`, `sh`, `head`, `tr`, `wc`, `printf`, `sleep` and `true`. A Windows program can't find them, and Wine, given one by its path, starts it without the standard handles or the exit code it was given. Before MYLA-705 the cases returned at the first spawn's `Unsupported`; now that spawn is `NotFound`. So `tests/burn/_targets.py` excuses `std.process` from `test_std_modules` on x86_64-windows, and its target-independent cases (`SpawnError`'s messages, `spawn_error_from_cause`, `stdio_letters`, …) with it. test_process's `WindowsChildren` covers the same ground with a Windows program of its own.

- [x] The cases' children are programs every target has: the harness's own executable in a mode of its own, or a helper that std.test builds, so the cases run on Windows too
- [x] `std.process` no longer excused on x86_64-windows

## What changed

- **The test tool** ([[lib/std/test.my]]'s `tool_mode`): the program that runs the cases, in a mode of its own, `<program> --test-tool <step>…`. Its steps run in order, then it ends with 0: `cat`, `upper` (`tr a-z A-Z`), `a-for-nul` (`tr '\0' a`), `head <n>`, `count` (`wc -c`), `line` (`read x; printf "$x"`), `out <text>`, `err <text>`, `zeros <n>`, `err-zeros <n>` (`head -c n /dev/zero`), `sleep <ms>`, `exit <n>`. It reads and writes the standard streams with the primitives alone (`__read_bytes`, `__write_bytes`), so the harness of no std module gains an import; a write to a pipe nobody reads ends it quietly, as by SIGPIPE (D146): `Signaled(13)` on Linux, `Exited(141)` on Windows.
- **Who runs it:** natively the harness, whose generated `#main` calls `tool_mode` first ([[selfhost/harness.my]]); interpreted `myla` itself, whose `main` calls it before reading its command ([[selfhost/main.my]], a hidden `myla --test-tool …`).
- **How a case finds it:** the primitive `__test_tool()`, beside `__test_dir()` and `__test_program()` ([[selfhost/checker.my]], [[selfhost/lower.my]], [[selfhost/codegen.my]]'s builtin names, [[selfhost/interp.my]]): natively the environment variable `MYLA_TEST_TOOL`, which std.test's runner sets for each case's child to its own path (`run_in_children`); interpreted the running `myla` as it was started, from the working directory when relative (`program_path`). No seed needs it: only std.process's cases call it, and the seed checks no std function nothing calls (D179).
- **The cases** ([[lib/std/process.my]]): each child is `tool([...])` (the program, under `MYLA_TEST_EMULATOR`'s emulator where the harness runs under one, as qemu-user starts no child under itself); `/dev/null` as a directory that is a file is the tool's own path; a kill's status is `killed()` (`Signaled(9)`, on Windows `Exited(1)`, D224) and a broken pipe's `broken_piped()` (`Signaled(13)`, on Windows `Exited(141)`), by `std.platform`'s `TARGET`. What each case checks is as before; the `SpawnError` lines changed only their program (the Interface lane changes `WorkingDir`).
- **The excuse** of `std.process` on x86_64-windows is gone from `tests/burn/_targets.py`'s `SKIP_PROGRAMS`; wasm32 needs none (its first spawn is `Unsupported`, which each case returns at).
- **Docs:** [[Language/Standard-library/Test]] (the test tool), [[Language/Standard-library/Rt]] (`test_tool`), the `myla` skill's toolchain reference (`MYLA_TEST_TOOL`).

## Proposals

1. **The cases' children are the test tool: the program running the cases, in a mode of its own** (built). Natively the harness (`<harness> --test-tool …`), interpreted `myla` (`myla --test-tool …`), found with `__test_tool()`. It needs no build and no file beyond the runner, runs at native speed interpreted too (16 MiB through `zeros | count`), and under Wine the harness's own `Z:\…\harness.exe` path, which the runner already starts its cases by. It costs every harness the tool's code: a program calling `run_in_children` is 109,520 bytes with `tool_mode`, 102,048 without (2026-11-16, this branch).
   - *A helper that std.test builds* (`myla test` compiles a `std/test_tool.my` for the target once a run and gives its path): a build per `myla test` that needs it (a link with lld-link for Windows), a way to tell which files need it, and for the interpreter a native build for the host besides.
   - *The cases run as a Myla script* (`myla run tool.my -- cat`): interpreted children, too slow for the 16 MiB and 50 MB pipes, and still the problem of finding `myla`.
   - *Each target's own programs* (`cmd.exe /c` and `findstr` on Windows): cases that differ by target, and Wine's `cmd` isn't Windows'.
   - *The tool only in harnesses that call `__test_tool()`*: saves the 7 KB elsewhere, but the generator would have to ask the checker which primitives the file's checked functions call.
2. **`__test_tool()` is a primitive of `myla test`'s, interpreted `myla`'s own path** rather than a pub `std.test` function or an environment variable read by the case: std.process's cases can't import std.test (it imports std.process, and every program importing std.process would load std.test), and an interpreter can't set its own environment. A pub `test.tool(steps) -> Command` for programs' own tests could come later; nothing needs it now.

Suggested decision rows:
- "**std's cases that start processes start the test tool** ([[MYLA-727]]): the program running the cases in a mode of its own, `<program> --test-tool <step>…` (the harness natively, `myla` interpreted; std.test's `tool_mode`), found with the primitive `__test_tool()` (natively `MYLA_TEST_TOOL`, which std.test's runner sets to its own path; interpreted the running `myla`), under `MYLA_TEST_EMULATOR`; its steps stand in for `cat`, `sh`, `head`, `tr`, `wc`, `printf`, `sleep` and `true` | Every target with processes has the program, Windows too, at native speed and without a build of its own; a helper built per run would cost a link per `myla test`, a script run interpreted would be too slow for the cases' pipes, each target's own programs would make the cases differ by target. Each harness carries the tool's code, about 7 KB"
