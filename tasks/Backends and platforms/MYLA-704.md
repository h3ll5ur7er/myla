## What changed

**The platform module** ([[lib/std/platform_windows.my]]): its file, directory, stat, path and working-directory functions over kernel32. A descriptor is the handle of the file or directory, and 0 to 2 the standard streams (`std_handle`; no handle is 0, 1 or 2), so `read`, `write`, `close`, `seek`, `fd_stat` take both, and a pipe's handle too ([[MYLA-705]]'s). A path crosses as UTF-16 (`wide`, `put_utf8`: a malformed character U+FFFD, D215) to `CreateFile2`, whose five arguments fit `__syscall5` (`CreateFileW` has seven), shared for reading, writing and removing as files are on Linux; `open_file` maps std.rt's portable flags (`disposition_of`; an append is `FILE_APPEND_DATA` without `FILE_WRITE_DATA`, every write at the end). A file's kind, size, time, volume and index come from `GetFileInformationByHandle` (`handle_stat`), a reparse point's tag says whether it is a link (`kind_of`), its permissions from the read-only attribute (`permissions_of`, D218); `path_stat` opens a path for its attributes only (`FILE_FLAG_OPEN_REPARSE_POINT` for a link itself). A directory is listed with `GetFileInformationByHandleEx`'s `FILE_ID_BOTH_DIR_INFO` records, each made a record of the module's own (its size, kind and name's length, the name in UTF-8): the records read into half the room are at most twice as long made ours. `seek` checks Linux's range (`SetFilePointerEx` from the start), `cwd` is `GetCurrentDirectoryW`'s, `make_dir`, `remove_file`, `remove_dir`, `rename` are `CreateDirectoryW`, `DeleteFileW`, `RemoveDirectoryW`, `MoveFileExW` (`MOVEFILE_REPLACE_EXISTING`).

Where Windows reports what Linux reports otherwise, the module gives Linux's cause, so a program prints the same on both: a directory opened or removed as a file IS_A_DIRECTORY (Windows: access denied; `open_handle`, `remove_file`), a path through a file NOT_A_DIRECTORY (a path not found: `path_failed` asks the directories before the last component for their attributes), a name past 255 units ENAMETOOLONG's `Other(36)`, a read or a write of a handle without that access BAD_HANDLE (`access_cause`, Linux's EBADF), a pipe's or the console's seek ESPIPE's `Other(29)`, a handle that isn't open BAD_HANDLE (`file_type`). Random bytes stay `Unsupported`: bcrypt is a second import library ([[MYLA-722]]).

**std.path on Windows' paths** ([[lib/std/path_windows.my]], new). As Python's `os.path` is `ntpath` on Windows, std.path is `path_windows.my` on x86-64 Windows: the same functions with the same types on Windows' paths, `\` a separator too, a drive or a UNC share (`\\srv\share`, `\\?\…`, `\\.\…`) before the root as `ntpath.splitroot` reads one, absolute as `ntpath.isabs`, `join` as `ntpath.join`; what it writes is `/`, as on every target. [[lib/std/path.my]] keeps Linux's rules, its behaviour on Linux unchanged; both gain `anchor` (where a path starts), which std.glob reads. A program on any target may import `std.path_windows`.

**A module's copy for a target** ([[selfhost/loader.my]]). `for_target` took a target's `std/platform.my`; it now takes a module's copy for the target too, named as the platform module is (`own_copy`: `path_windows.my` for `std/path.my`, `path_style_windows.my` for `std/path_style.my`), from the library the tools carry and the stdlib root, and leaves a module the caller gives a text of its own (a test harness: `myla test lib/std/path.my --target x86_64-windows` runs that module's cases). No primitive, runtime variable or attribute is new: **no `Stage:` commit**.

**std.fs and std.glob** read `std.path_style.WINDOWS` ([[lib/std/path_style.my]], one constant, and its Windows copy). On Windows `make_dir_all` splits at `\` too and starts after a UNC share (`share_end`), `temp_root` is `%TMPDIR%`, `%TEMP%` or `%TMP%` (else `.`), `joined` takes a directory ending in `\`; std.glob splits a path at `\` too (a pattern's `\` still escapes) and matches an absolute pattern from its anchor, a drive of either case alike (`Pattern.root`, `same_root`).

**Tests.** `tests/burn/test_windows.py`: `test_files_and_directories` (names in UTF-8, an append, a listing, metadata, the errors as Linux's) and `test_windows_paths` (std.path's Windows rules, the working directory `Z:\…`, std.glob and `make_dir_all` on it); `test_what_isnt_there_yet_says_so` now checks random bytes. `test_platform_interface.TargetCopies`: the copies declare what their modules declare. `path_windows.my`'s 110 cases, `platform_windows.my`'s new ones (the conversions, `disposition_of`, `kind_of`, `permissions_of`), std.glob's `backslashes`, std.fs's `share_end` and `root_of`. `test_fs.test_current_dir` expects Windows' path for the native run under Wine; `prepare_tree` makes no Unix links for Windows (Wine would show them as directories).

## Proposals (accepted 2026-11-15: the first two are D223, the other three stand as built, D227)

1. **std.path is a module per path style, the loader taking Windows' for the target** (built). Python's `posixpath`/`ntpath` design: `path.my` (Linux's and WASI's rules, unchanged) and `path_windows.my`, with the same functions (a test holds them to it), and a one-constant `path_style.my` with a Windows copy for std.fs and std.glob. Alternatives: (a) one `path.my` with both rule sets behind a flag; built first, it is a single source, but checking any program that calls `path.join` then checks the Windows rules too, 26.2 M → 29.9 M instructions (+14 %, with the carried library, 2026-11-15, against `194c9dc`) on every target; (b) the flag read from std.platform (`WINDOWS_PATHS` beside `PROCESSES`), no loader change, but importing std.platform's 2,000 lines made checking a program that imports std.fs 48.7 M → 59.2 M instructions and std.path 26.2 M → 40.4 M (the owner wrote std.fs's `hex_of` to save 1.4 M); (c) declarations chosen per target ([[MYLA-245]]'s `cfg`), the real fix, a language feature. Proposed row: *"A module of the standard library may have a copy for a target, named as its platform module is (`std/path_windows.my` beside `std/platform_windows.my`), which the loader takes for it there (`for_target`); std.path is Windows' on Windows as Python's `os.path` is `ntpath`, and what it writes is `/` on every target ([[MYLA-704]], D215)."*
2. **What std.path writes on Windows is `/`** (built): `join`'s separator and the ones `normalize` and `relative` build with, so a program builds the same paths on every target (D215's same bytes), and Windows reads them; a prefix stays as written, and what is taken out of a path keeps its separators. Alternative: `\`, as Python's `ntpath` and Rust's `PathBuf` write, the native look (`C:\a\b`), but `path.join("src", "lib/main.my")` would print otherwise on Windows, and so would every glob result built with it (std.glob's suites compare the same text on every target).
3. **Absolute on Windows is `ntpath.isabs`'s** (built): a drive and a root, or a UNC prefix; `\a` (the working directory's drive) and `C:a` aren't, as in Python 3.13 and Rust. `join` still lets a rooted `\b` replace `a`'s path and keep its drive. Alternative: Python's older rule, a root alone absolute.
4. **Windows' errors that Linux reports otherwise are Linux's** where a program sees them (built): a directory opened or removed as a file `IsADirectory`, a path through a file `NotADirectory`, a too long name `Other(36)`, a read of a write-only `File` `Other(9)`, so one program prints the same on both. Alternative: Windows' own (`PermissionDenied`, `NotFound`, as Rust gives), which costs nothing but differs per target.
5. **`temp_root` on Windows** is `%TMPDIR%`, `%TEMP%`, `%TMP%`, else `.` (built), as Python's `tempfile` looks (its last resort the working directory). Alternative: `GetTempPath2W` (the same variables, then `%USERPROFILE%`, then the Windows directory), a kernel32 call.
