The numeric toolbox that `std.jpeg`, `std.imgproc`, `std.ai` and the planned GUI system will build on. The owner's shape (2026-11-13): the common fixed sizes as their own types, plus a slower generic type of any size whose dimensions are checked at run time.

- `std.vector`: `Vec2`, `Vec3`, `Vec4` (structs `{ x, y[, z[, w]] }`), and `Vector`, any length (`[float]` inside; a size mismatch is a runtime error that names both sizes).
- `std.matrix`: `Mat2`, `Mat3`, `Mat4`, and `Matrix`, any `rows × cols` (one flat list inside; shapes checked at run time).
- `std.quaternion`: `Quat` (from axis and angle, from Euler angles, to `Mat3`/`Mat4`, `slerp`, rotating a `Vec3`).
- Operators wherever they read naturally, through [[MYLA-584]]: `+ -` between same-sized values, `*` and `/` by a scalar on either side, `Mat * Vec`, `Mat * Mat`, `Quat * Quat`, `Quat * Vec3`, unary `-`, and the compound forms (`pos += vel * dt`). Named methods for the rest: `dot`, `cross`, `length`, `length_squared`, `normalized`, `distance`, `lerp`, `transpose`, `determinant`, `inverse` (an `Option`), `identity`, the 3D transforms (`translation`, `rotation_*`, `scaling`, `look_at`, `perspective`, `orthographic`).
- `#derive(Eq, Hash)` (with [[MYLA-586]]), `impl Format` (`f"{v}"` as `(1, 2, 3)`), `#derive(Json)` where it fits.

Depends on [[MYLA-584]] (operators between different types) and [[MYLA-585]] (float methods). Building it first with methods only would give the library an API to rewrite.

## Open questions for the owner

- [x] Element type (D199: both; `std.vector32` etc., the float32 twins, generated with the float64 modules from one template): `float64` only (Myla's `float`); also `float32` variants for graphics and GPU upload (`Vec3f`/`Mat4f`, or `Vec3<T>` generic with `T: Float`, which needs a numeric trait and spells `Vec3<float>` everywhere since type parameters have no defaults)
- [x] Matrix storage and multiplication convention (D199: column-major, column vectors, right-handed): column-major and column vectors (OpenGL, glam, most GPU APIs) or row-major
- [x] Construction (D199: free functions and `std.algebra`'s `Zero`, `One`, `Identity`): Myla has no static functions, so `vector.vec3(1.0, 2.0, 3.0)`, the struct literal after `from std.vector import Vec3`, and `Vec3.zero()` through a trait with functions without `self` (D172), say `Zero`/`One`/`Identity` in a small `std.num`-level trait module
- [x] Indexing `v[0]` and `m[r, c]` needs an `Index` trait (done in MYLA-584: `v[0]`, `m[(r, c)]`, `m[i]` a column) (an open question in [[MYLA-584]]); until then `v.at(i)`, `m.at(r, c)`

## Evidence

- Built as D199: `std.algebra` (`Zero`, `One`, `Identity`; `Zero`/`One` on every number type; `sum`, `product`) and six generated modules, std.vector/matrix/quaternion in float64 and their `32` twins in float32 (`scripts/gen_std_linalg.py`, `--check` asserted by `test_linalg`): `Vec2`–`Vec4`, `Mat2`–`Mat4` (column-major, column vectors, right-handed), `Quat`, `Vector` and `Matrix` of any size with their shapes checked at run time, the transforms (`translation` … `rotation_axis`, `look_at_rh`, `perspective_rh_gl`/`perspective_rh`, `orthographic_rh_gl`/`orthographic_rh`, the 2D ones), conversions between the precisions.
- Before writing them, a prototype confirmed what the library leans on: operators by type arguments across modules, `Vec3.zero()` through a trait of a third module, an impl on `float64` in a std module, two modules each with a `Vec3`, the twins importing each other.
- Found and fixed on the way (MYLA-584's code): a number literal beside a classic impl and one by type arguments now takes the type of the impl its kind picks (`v * 2.0` on a float32 vector with both `Mul` and `Mul<float32>`; `operand_hint`), also after a struct literal (`Narrow { v: 1.5 } * 2.0`); `#test` cases above an operator method renamed for its right operand were skipped by both runners (`is_qualified` read the `$` of `mul$float64` as another module's) and the native harness called the classic method instead: it now calls them through their operators. `test_operator_traits` covers both (4/4).
- Tests: `tests/burn/test_linalg.py` 3/3 (the program alike interpreted, natively and as wasm32; a shape mismatch the same runtime error at the same place; the generated files current); module cases interpreted and `--native`: vector 15/15, vector32 15/15, matrix 5/5, matrix32 5/5, quaternion 1/1, quaternion32 1/1, algebra 1/1.
- The conventions checked independently: a Python reimplementation of the model-view-projection from the textbook formulas (row-major math, column vectors) puts the example's first and last cube corners at (243, 275) and (405, 164), as `examples/transforms.my` prints.
- `examples/transforms.my` (4/4 cases), registered; the wiki pages [[Language/Standard-library/Algebra]], [[Language/Standard-library/Vector]], [[Language/Standard-library/Matrix]], [[Language/Standard-library/Quaternion]] with tested examples; [[Language/Standard-library]], [[Development/Testing]], the skill.
