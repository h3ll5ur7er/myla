Myla does not pass C beyond the cache

The first FFT report listed Myla at 0.95 times C for a million points. That number was measurement noise. Re-timed across eleven sizes, Myla is slower than C at every one: times in the cache and still times at a million points.

What is real is that the gap narrows. Myla pays a fixed extra cost per butterfly. Once the data outgrows the cache, both programs wait for the same memory, and that shared wait makes the fixed cost a smaller share of the total.

The two lines never cross. They rise together past about 87,000 points, where the 24 bytes per point (signal plus table of factors) no longer fit this machine's 2 MB second-level cache. The distance between them stays between about 5 and 10 ns throughout.

Why the first report was wrong

That run timed each program five times on a shared cloud VM, at one large size, and reported the median. At that size single runs of the same binary differed by up to 2.1 times. C happened to draw slow runs and Myla fast ones. The report flagged the panel as unreliable, but the 0.95 was still printed, and it should not have been read as a result.

Whole-program counts divided by 20,971,520 butterflies, so setup is included and the figures are approximate. Raw counts: instructions 951 M and 4,072 M; data accesses 246 M and 1,595 M; misses past the 2 MB cache 41.8 M and 45.9 M.

Both programs touch the same elements in the same order, so they miss the cache almost equally. Myla's extra work is about 65 additional memory accesses per butterfly that always hit the first-level cache: list pointers reloaded from self, list lengths read for bounds checks, and intermediate values kept on the stack. They cost a few nanoseconds whatever the data size.

Method

  • The same programs as the first report: an in-place radix-2 FFT, identical operation for operation in C and Myla, with identical checksums. C is built with gcc 16.2 at -O2 -ffp-contract=off; Myla with myla build.
  • Each size runs about 134 million butterflies, five times, pinned to one CPU. The fastest run is the least disturbed one, so the table and the lines use it.
  • Machine: Intel Xeon at 2.1 GHz, 4 virtual CPUs, 48 KB first-level and 2 MB second-level cache per core, a shared cloud VM. It was a different, slower host than the first report's, so compare shapes and ratios, not absolute times.
  • Script: benchmarks/fft/sweep.py in the Myla repository.
