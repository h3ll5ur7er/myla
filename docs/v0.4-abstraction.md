# Myla v0.4 — Abstraction (design)

This is the detailed, decision-complete design for the **v0.4 "abstraction"**
milestone — Tier D in [self-hosting.md](self-hosting.md) §3. It expands the
sketches in [future-features.md](future-features.md) §3/§5/§6/§14 into a real
specification: concrete syntax, semantics, grammar (EBNF), type-system changes,
and an implementation plan across the existing lexer → parser → checker →
interpreter → compiler pipeline.

**Scope (v0.4):**

1. **Methods & `impl` blocks** — `recv.method(args)`, `self` / `var self`,
   static dispatch (D27).
2. **Lambdas & closures + function types** — anonymous functions as values,
   by-value capture (D15), `(A, B) -> R` types.
3. **Functional pipelines** — `|>` pipeline, `>>` composition (by operand type,
   D24), `_`-placeholder partial application (D8).
4. **Traits + operator overloading** — `trait` / `impl Trait for T`, built-in
   operators desugaring to trait methods, a derivable structural `Eq` (D18, D37).

Out of scope (later tiers): modules & imports and the stdlib (v0.5), the Unicode
`char` type and the freestanding I/O runtime (v0.5), trait **objects** / dynamic
dispatch, generic **trait bounds** beyond the minimal form in §4, custom
operators (post-1.0, D18), and `++`/`--`/compound-assignment sugar (post-1.0).
Dispatch stays **static** and everything is **monomorphized** — no vtables, no
runtime type tags, consistent with v0.2/v0.3.

> The sub-decisions this design raises (**X1–X9**) are now **locked** as
> **D45–D53** in [roadmap.md](roadmap.md). This document reflects those decisions;
> the “(see Xn)” markers point at the originating question for provenance.

## 1. Methods & `impl` blocks

### 1.1 Syntax

```my
struct Lexer { src: str, pos: int }

impl Lexer {
    fun peek(self) -> uint8 {
        return self.src[self.pos]
    }
    fun advance(var self) {            // mutating method — needs a `var` receiver
        self.pos = self.pos + 1
    }
    fun slice(self, n: int) -> str {   // ordinary extra params follow `self`
        // ...
    }
}

var lx = Lexer { src: "ab", pos: 0 }
let c = lx.peek()        // 97
lx.advance()             // ok: lx is a `var`
```

- An `impl T { … }` block attaches **methods** to a named type `T`. Each method
  is a `fun` whose **first parameter is the receiver**, written `self` (read-only,
  by value) or `var self` (mutating). Additional parameters follow normally.
- Call syntax is `receiver.method(args)`. This is the **only** surface call form
  for a method; internally it lowers to `T::method(receiver, args)` (D27). Method
  names live in a **per-type namespace**, not the global function namespace (see
  X2) — so a method `len` never collides with the `len` builtin or a free `fun`.

### 1.2 Which types can have an `impl`? (see X1 — coherence)

Myla is *inspired by* Rust, not a copy of it — and it deliberately trades some of
Rust's safety for simplicity (README "Visions"). So there is **no orphan rule and
no origin-based restriction**: any type may have inherent and trait methods,
regardless of whether the type or the trait is user-defined or built-in.

- **Inherent `impl`** is allowed for **any named type** — user-defined `struct`/
  `enum`, the prelude enums (`Option`/`Result`), and the built-in scalar/collection
  types (`int…`, `bool`, `str`, `uint8`, `[T]`, `[K: V]`, `StringBuilder`). v0.4
  has no modules, so coherence is **whole-program**: the union of all `impl T`
  blocks defines `T`'s method set. (Tuples and bare function types take no
  inherent `impl` — they have no name to attach methods to; wrap them in a struct
  if you need methods.)
- **Multiple `impl T` blocks** for the same `T` are allowed (e.g. one inherent,
  several `impl Trait for T`); the method names across all of them must be
  **unique per type**, and must not collide with a field name of `T`. A duplicate
  *method name* is a compile error (`duplicate method 'm' for type T`).
- **Free mix-and-match of traits and types** (the project owner's call): a
  user trait on a built-in type, a built-in trait on a user type, *and* a built-in
  trait on a built-in type are **all allowed**. Built-in types ship with
  **implicit default impls** of the built-in operator traits (the hardwired
  v0.0–v0.3 semantics, §4.2); a user `impl Trait for T` for the same
  `(Trait, T)` pair **overrides** that implicit default. The only hard
  constraint is **uniqueness**: at most one *user* impl of a given trait for a
  given type (two user impls for the same pair is an ambiguity error). The
  compiler trusts the author — e.g. an `impl Add for int` whose body is nonsense
  is the author's problem, not a rejected program ("simplicity over safety").

### 1.3 `self` semantics (see X3)

- `self` has the receiver type `T` and **value semantics** like any parameter:
  for heap-backed `T` (a list/map/string-builder field, a recursive enum) the
  receiver is shared by refcount and copy-on-write applies on mutation.
- `self` (read-only): the body may read `self` and its fields but not assign
  through it; calling a `var self` method on `self` is rejected.
- `var self` (mutating): the body may assign `self.field = …`, call other
  `var self` methods, and mutate `self`'s collections in place. A `var self`
  method **requires a mutable lvalue receiver** — exactly the rule used for
  `push`/`m[k] = v` (D40). `tmp().advance()` on a temporary is a compile error
  (`cannot call mutating method on a non-mutable value`), as is `let x = …; x.advance()`.
- There is no UFCS free-function spelling (X2): you cannot write
  `Lexer::peek(lx)` or `peek(lx)` in source; `lx.peek()` is the call form.

### 1.4 Method resolution

- The checker resolves `recv.method(args)` by the **static type** of `recv`:
  look up `method` in `T`'s method set (inherent + trait impls), then check the
  argument arity/types against the (post-receiver) signature, and the receiver
  mutability against `self` vs `var self`. `T` may be a built-in type, so
  `xs.sorted()` / `(5).clamp(0, 9)` resolve the same way as `lx.peek()`.
- Field access and method calls share the `.` operator but are disambiguated by
  the trailing `(`: `recv.x` is a field, `recv.x(args)` is a method call. A
  method and a field may not share a name (§1.2), so there is no ambiguity.
  (Calling a method directly on an integer literal — `5.clamp(…)` — requires
  parenthesizing the literal, `(5).clamp(…)`, so the lexer never mistakes the
  `.` for the start of a future float literal; calling on a binding is
  unambiguous.)
- Resolution is **static** — the concrete receiver type is always known after
  type-checking (no trait objects), so dispatch is a direct `call`.

### 1.5 Generic `impl`

```my
struct Box<T> { value: T }

impl<T> Box<T> {
    fun get(self) -> T { return self.value }
    fun set(var self, v: T) { self.value = v }
}
```

- `impl<T> Box<T> { … }` introduces the type parameters used by the methods.
  Methods on a generic type are monomorphized **with** the type: stamping
  `Box<int>` stamps `Box<int>::get`, `Box<int>::set`, etc., reusing the v0.2.4b
  layout-monomorphizer and name-mangling. Method type parameters beyond the
  receiver's (`fun map<U>(self, f: …)`) monomorphize at the call site like any
  generic function (v0.2.4a).

### 1.6 Lowering & codegen

- The checker rewrites each `recv.method(args)` to a direct call of the lowered
  function `T::method` with `recv` threaded as the first argument; RC retain/drop
  of the receiver follows the existing argument rules (`var self` writes back
  through the lvalue under CoW, like a mutating intrinsic).
- The native backend emits one ordinary function per (monomorphized) method —
  no vtables, no receiver boxing. The interpreter binds `self` in the call frame
  and evaluates the body like any function.

## 2. Function types, lambdas & closures

### 2.1 Syntax

```my
let add = (a: int, b: int) => a + b          // expression body
let greet = (name: str) => {                 // block body (uses `return`)
    let msg = "hi " + name
    return msg
}

fun apply(f: (int) -> int, x: int) -> int {  // function-typed parameter
    return f(x)
}

let g: (int, int) -> int = add               // function type annotation
print(apply((n) => n * n, 5))                // 25
```

- A **lambda** `(params) => body` is an anonymous function value. The body is
  either an **expression** (its value is returned) or a **block** `{ … }` (which
  returns via `return`, like a `fun`).
- **Function types** are written `(T0, T1, …) -> R`. A no-arg function is
  `() -> R`; a void result is written by omitting `-> R` only in `fun`
  declarations — function *types* always name a result, using the existing
  "no return type" convention internally (a `void` function value is typed
  `(…) -> ()`-less; in practice lambdas used as statements are rare and a
  `() -> R` shape covers the self-hosting needs). Parameter types are required in
  lambdas (no whole-program inference); the checker still applies the usual
  integer-literal flexibility against an expected function type.

### 2.2 Capture (see X4 — by value, D15)

- A lambda may reference variables from the enclosing scope; those are
  **captured by value** at the point the lambda is created (a snapshot copy,
  honoring deep immutability D14). By-reference capture is deferred to a later
  `ref` form (D15).
- Capturing a heap-backed value (list/map/string-builder/recursive enum/string)
  **retains** it into the closure's environment; the environment is dropped (and
  its captures dropped) when the closure value itself is dropped.
- Mutating a captured variable inside the lambda mutates only the **copy** in the
  environment, never the original binding — consistent with by-value parameters.

### 2.3 Representation (see X5)

- A function value is a **16-byte fat value**: `(code_ptr, env_ptr)`.
  - `code_ptr` points at a lifted top-level function whose first hidden parameter
    is the environment pointer.
  - `env_ptr` points at a **refcounted heap cell** holding the captured values
    (`[refcount, <captures…>]`, laid out like a struct). A **non-capturing**
    lambda uses `env_ptr = 0` (null), and its lifted function ignores the env.
- A plain top-level `fun` referenced as a value (e.g. passed to `apply`) becomes
  a function value with `env_ptr = 0` and a `code_ptr` that ignores the env, so
  `fun`s and lambdas share one calling convention.
- Calling `f(args)` loads `code_ptr`/`env_ptr` from the fat value and calls
  `code_ptr(env_ptr, args…)`. The environment cell is a normal RC owner: retained
  on copy of the function value, dropped at scope exit, freeing captures at zero.
- **Lambda lifting**: each lambda becomes a stamped top-level function
  `__lambda_<n>` plus an env layout; closures over generic type parameters are
  monomorphized with their enclosing function.

**Forward-compatibility with `ref` capture (D15).** This is the same
representation OCaml/Rust-style closures use for mutable upvalues, so adding
by-reference capture later is **additive**, not a redesign:

- A `ref`-captured local is **heap-promoted to a refcounted box** at its
  declaration; the env slot then holds a **pointer to that box** instead of an
  inline copy, and both the original binding and the closure read/write through
  it (shared mutation).
- What stays identical: the 16-byte fat-value layout, the calling convention
  (`code_ptr(env_ptr, …)`), and how by-value captures work. Only two things get
  added — env slots become heterogeneous (inline value *or* box pointer), and
  `ref`-captured locals are boxed. The box's lifetime rides the existing RC
  machinery (memory-safe even if the closure escapes).
- Cost is opt-in: only `ref`-captured variables pay the extra indirection.
- To keep that path smooth, v0.4 already routes **all** captured-variable access
  through the env uniformly, so flipping a slot from "inline copy" to "box
  pointer" is a localized change. `ref` reintroduces shared mutable state with no
  borrow checker — a deliberate escape hatch the author opts into (consistent
  with "simplicity over safety").

### 2.4 Interpreter

- A runtime `ClosureValue { code, env }` where `code` is the (possibly lifted)
  callable and `env` is a dict/struct of captured **copies**; calling it binds
  parameters + captures and evaluates the body. Deep-copy on capture mirrors the
  native by-value semantics.

## 3. Pipelines, composition & partial application

All three are **pure desugaring** over §2 lambdas/calls — no new runtime.

### 3.1 Pipeline `|>` (see X6)

```my
let n = 5 |> double |> inc        // == inc(double(5))
let m = 5 |> add(3)               // == add(5, 3)  (left value becomes 1st arg)
```

- `x |> f` ≡ `f(x)`; `x |> f(a, b)` ≡ `f(x, a, b)` — the left operand is spliced
  as the **first argument** of the right-hand call. `|>` is a new token at the
  **lowest binary precedence** (below `||`), **left-associative**.
- The right operand must be callable (a function value, a method-free `fun`, or a
  call expression whose callee is callable); otherwise a type error.

### 3.2 Composition `>>` (operand-typed, D24)

```my
let process = double >> inc >> to_str   // (x) => to_str(inc(double(x)))
print(process(5))                       // "12"
```

- When **both operands are function-typed**, `a >> b` ≡ `(x) => b(a(x))`
  (left-to-right). When both operands are **integers**, `a >> b` is the v0.3
  right shift. Mixed operands are a type error. The disambiguation happens in the
  checker by operand type (D24); the parser keeps treating `>>` as the existing
  adjacent-`>`/`>` shift-precedence operator and the checker reinterprets it.
- Result arity: composition requires `a`'s result type to match `b`'s single
  parameter type; the composed value has type `(A) -> C` where `a: (A) -> B`,
  `b: (B) -> C`.

### 3.3 Partial application `_` (see X7)

```my
let add5 = add(5, _)        // (b) => add(5, b)
let half = div(_, 2)        // (a) => div(a, 2)
xs |> map(double) |> filter(gt(_, 3))
```

- A call with one or more `_` arguments produces a **lambda** whose parameters
  are the holes, left-to-right, with the non-hole arguments captured by value.
  No implicit auto-currying — a missing argument without `_` is still an arity
  error (keeps mistakes loud).
- `_` is only meaningful in **argument position** of a call; elsewhere it is a
  parse/type error (`'_' placeholder is only valid as a call argument`).
- **Holes work in method calls too** (desugaring is purely syntactic, so it does
  not need UFCS, X2): `obj.scale(2, _)` ≡ `(b) => obj.scale(2, b)` — the receiver
  and the filled arguments are captured by value, the holes become the lambda's
  parameters.

### 3.4 Methods vs. pipelines/composition (X2 interaction)

Methods (`recv.method(args)`) and the functional operators cover **different call
forms that both read left-to-right**, so no-UFCS (X2) is not a limitation here —
they are complementary:

- **Method chaining** is the left-to-right flow *for methods*:
  `lexer.peek().is_digit()`. No `|>` needed — `.` already chains.
- **`|>`** is the left-to-right flow *for free functions*: `5 |> double |> inc` —
  precisely the case method chaining can't express (no receiver).
- **`_` partial application** works on both free calls and method calls (above).
- **`>>` composition needs a function *value***; a method is not one (X2), so to
  compose a method, wrap it in a lambda: `process = (x) => x.sorted() >> ...`.
  This is the only friction, and it is a one-liner.

This keeps the door open: a method-reference value (`.method` / `Type::method`)
or full UFCS can be **added later** as a non-breaking extension if a concrete need
appears — whereas making every method a free function now would permanently merge
the value namespace (and collide with builtins like `len`/`push`). Start
restrictive; expand only on demand.

## 4. Traits & operator overloading

A **minimal** trait system, sufficient for operator overloading and a derivable
structural `Eq` — the two things v0.2/v0.3 explicitly deferred to "traits in
v0.4" (D18, D37). Trait **objects** and broad generic **bounds** stay out (see
X8/X9 for the limited bound form included). Per §1.2 there is **no orphan rule**:
any trait may be implemented for any type, in any user/built-in combination.

### 4.1 Declaring & implementing

```my
trait Add {
    fun add(self, other: Self) -> Self
}

struct Vec2 { x: int, y: int }

impl Add for Vec2 {
    fun add(self, other: Vec2) -> Vec2 {
        return Vec2 { x: self.x + other.x, y: self.y + other.y }
    }
}

let v = Vec2 { x: 1, y: 2 } + Vec2 { x: 3, y: 4 }   // desugars to Vec2::add(...)
```

- A `trait` is a named set of **method signatures** (with `self`/`var self`
  receivers). `Self` denotes the implementing type. Default method bodies are
  **out of scope** for v0.4 (every signature must be implemented).
- `impl Trait for T { … }` provides the trait's methods for `T` — for any `T`,
  user-defined or built-in (§1.2). The checker verifies the impl covers exactly
  the trait's signatures (no missing, no extra), with matching receiver
  mutability and (Self-substituted) parameter/return types.
- Trait methods join `T`'s per-type method set (§1.2) and are callable as
  `recv.method(args)`. Coherence: at most one **user** `impl Trait for T` per
  `(Trait, T)` pair (whole-program); a second user impl for the same pair is an
  error. A user impl for a pair that has a built-in **implicit default** (§4.2)
  overrides that default rather than conflicting with it.

### 4.2 Built-in operator traits (see X8)

A **fixed** set of built-in traits backs the overloadable operators. `a OP b`
desugars **uniformly** to the corresponding trait method on the operand type;
resolution then finds either a user `impl` or the type's built-in default. The
primitive types ship with **implicit default impls** of these traits (the
hardwired v0.0–v0.3 semantics), which a user `impl` may override (§1.2 — the
author takes responsibility). For primitive operands with no user override, the
desugared call compiles straight to the existing inline instruction sequence — so
there is **no runtime cost** to the desugaring.

| Trait | Method | Operator(s) |
|-------|--------|-------------|
| `Add` | `add(self, other: Self) -> Self` | `+` |
| `Sub` | `sub(self, other: Self) -> Self` | `-` (binary) |
| `Mul` | `mul(self, other: Self) -> Self` | `*` |
| `Div` | `div(self, other: Self) -> Self` | `/` |
| `Rem` | `rem(self, other: Self) -> Self` | `%` |
| `Eq`  | `eq(self, other: Self) -> bool`  | `==`, `!=` (negated) |
| `Ord` | `cmp(self, other: Self) -> int`  | `< <= > >=` (sign of result) |

- Both operands of an overloadable binary operator must be the **same type**
  (no implicit mixing, D4); the result type is the trait method's result.
- `Eq`/`Ord` lift the v0.2 restriction (D37) for types that implement them:
  `==` on a `struct`/`enum`/tuple becomes `Eq::eq`. Primitives keep their
  built-in `==`/ordering as their implicit default `Eq`/`Ord`.

### 4.3 Derivable structural `Eq` (see X8)

```my
#derive(Eq)
struct Point { x: int, y: int }

let same = Point { x: 1, y: 2 } == Point { x: 1, y: 2 }   // true
```

- `#derive(Eq)` on a `struct`/`enum` synthesizes a structural `eq` (field-by-field
  / variant-and-payload), implemented in terms of the components' own `Eq`
  (primitives built-in; nested user types must themselves be `Eq`). This is the
  ergonomic answer to D37 and removes most hand-written `match`-equality.
- `#derive` is a built-in attribute (reusing the v0.0 attribute registry). The
  initial allow-list is **`Eq` only** — it's the most important and the direct
  answer to D37. **`Ord` is the planned next addition** (not necessarily in the
  first v0.4.4 cut); other derives can follow. Deriving an un-derivable shape (a
  field type without `Eq`) is a compile error.

### 4.4 Limited generic bounds (see X9)

```my
fun sum_all<T: Add>(xs: [T], zero: T) -> T {
    var acc = zero
    for x in xs { acc = acc + x }      // `+` allowed: T is bounded by Add
    return acc
}
```

- A type parameter may carry a **single built-in-trait bound** `T: Trait`
  (multiple via `T: A + B`). Inside the function, operators / methods named by
  the bound are usable on `T` values. Bounds are checked at the **call site**
  during monomorphization (the concrete `T` must have the required `impl`), so
  there is still no dynamic dispatch — an unsatisfied bound is a compile error at
  the call. User-defined trait bounds (beyond the built-in set) are deferred to
  v0.5; this minimal form is what generic numeric/`Eq` code in the self-hosted
  compiler needs.

## 5. Grammar additions (EBNF)

Extends [grammar.md](grammar.md), [v0.2-data-modeling.md](v0.2-data-modeling.md)
§6, and [v0.3-collections-and-ops.md](v0.3-collections-and-ops.md) §8.

```
/* --- top-level declarations --- */
decl_body   ::= … | impl_decl | trait_decl
impl_decl   ::= "impl" generic_params? type ( "for" type )? "{" method* "}"
trait_decl  ::= "trait" IDENT generic_params? "{" method_sig* "}"
method      ::= attribute* "fun" IDENT generic_params? "(" receiver ( "," param )* ")" ret? block
method_sig  ::= "fun" IDENT generic_params? "(" receiver ( "," param )* ")" ret?
receiver    ::= "var"? "self"
ret         ::= "->" type

/* --- types --- */
type        ::= … | fn_type
fn_type     ::= "(" ( type ("," type)* )? ")" "->" type

/* --- expressions --- */
primary     ::= … | lambda
lambda      ::= "(" ( param ("," param)* )? ")" "=>" ( expression | block )
call_arg    ::= expression | "_"                     /* `_` = partial-application hole */
postfix_op  ::= … | "." IDENT "(" arg_list? ")"      /* method call */

/* binary precedence, loosest→tightest (additions in **bold**):
   **|>** , || , && , (== !=) , (< <= > >=) , | , ^ , & , (<< **>>**) , (+ -) , (* / %) , cast
   `>>` reused for composition (operand-typed, D24); `|>` is the new loosest level */
```

New reserved keywords: `impl`, `trait`, `self`. (`Self` is a contextual type name
inside traits/impls; `=>` and `|>` are new tokens; `_` already lexes as an
identifier and is special-cased in argument position.)

## 6. Implementation notes (per pipeline stage)

- **Lexer:** new tokens `=>` (fat arrow) and `|>` (pipe-greater); keywords
  `impl`, `trait`, `self`; `->` already exists.
- **Parser:** `impl`/`trait` decls with method bodies/signatures and `self`/`var
  self` receivers; function types `(…) -> R` in type position; lambdas (with the
  `(`-lookahead disambiguation between a lambda param list and a parenthesized
  expression — decide by scanning to a matching `)` followed by `=>`); method-call
  postfix `.ident(args)`; `_` holes in argument lists; `|>` at the lowest binary
  level; `#derive(…)` attribute parsing (already an attribute slot).
- **Checker:** per-type method tables + coherence (X1); receiver-mutability rules
  (X3); function-type unification and lambda body inference; closure capture
  analysis (which free vars to snapshot) (X4); pipeline/composition/partial-app
  desugaring to calls/lambdas (X6/X7); trait/`impl` conformance + operator→trait
  resolution + derivable `Eq` synthesis (X8); call-site bound checking (X9).
- **Monomorphizer:** stamp methods with their type (generic `impl`s), lift
  lambdas to top-level functions + env layouts, stamp generic methods/closures
  per instantiation, and reify operator-trait method calls (X5/X8/X9).
- **Interpreter (erasure):** bind `self` in method frames; a `ClosureValue`
  capturing deep-copied env values; desugared pipelines/partial-app evaluate as
  ordinary calls; operator dispatch consults user `impl`s before built-ins.
- **Compiler (x86-64):** methods are ordinary monomorphized functions (receiver =
  first arg; `var self` writes back via CoW); function values are 16-byte
  `(code_ptr, env_ptr)` fat values with a refcounted env cell (retained/dropped
  by the existing RC walker, captures dropped at zero); calls load both halves
  and `call *code_ptr`; operator overloads compile to the resolved method call.

Every feature follows the project conventions: a runnable example with `#test`
cases (`examples/*.my`), interpreter↔native parity in the burn suite, and a
negative case in `examples/errors/` for each new diagnostic.

## 7. Suggested implementation phasing

Each phase lands end-to-end (checker + both backends + tests) before the next:

1. **v0.4.1 — methods & `impl`** (no traits yet): inherent `impl` on
   `struct`/`enum` (incl. generic `impl<T>`), `self`/`var self`, `recv.method()`
   resolution + lowering, static dispatch. *Foundation for everything else.*
2. **v0.4.2 — function types, lambdas & closures**: `(…) -> R` types, lambdas
   (expr + block body), by-value capture, the 16-byte fat-value representation +
   RC env cell, passing/returning/storing function values.
3. **v0.4.3 — pipelines, composition & partial application**: `|>`, `>>`
   compose-by-type, `_` holes — pure desugaring atop v0.4.2.
4. **v0.4.4 — traits + operator overloading + derivable `Eq`**: `trait` /
   `impl Trait for T`, the built-in operator traits, `#derive(Eq)`, and the
   limited generic bounds (X9).

Trait objects, default trait methods, and user-trait generic bounds remain
deferred (v0.5+); custom operators stay post-1.0 (D18). (Methods/trait impls on
built-in types are **in scope** from v0.4.1 — there is no orphan rule, §1.2.)

## 8. Sub-decisions (locked as D45–D53)

| # | Question | Recommendation |
|---|----------|----------------|
| **X1** | `impl` coherence: which types, how many blocks? | **No orphan rule / no origin restriction** — any trait (user or built-in) on any type (user or built-in), freely mixed. Inherent + trait `impl` allowed on any named type (incl. builtins); multiple blocks allowed; method names unique per type and distinct from fields; at most one *user* impl per `(Trait, T)`; a user impl overrides a built-in implicit default. Whole-program coherence. |
| **X2** | UFCS? Are methods also global functions? | **No UFCS.** Methods live in a per-type namespace; `recv.method(args)` is the only call form (`T::method` is internal lowering). Complementary to the functional operators: method chaining is the left-to-right flow for methods, `|>` for free functions; `_` partial application works on method calls too; `>>` composes function values (wrap a method in a lambda). Reversible: a method-reference value or UFCS can be added later as a non-breaking extension. (§3.4) |
| **X3** | `self` mutability & receiver rules | `self` by value (read-only); `var self` mutates and **requires a mutable lvalue receiver** (same rule as `push`/`m[k]=v`, D40); no mutating calls on temporaries/`let`s. |
| **X4** | Closure capture mode | **By value** (snapshot copy at creation), retaining heap captures into the env; mutation affects only the copy (D15). `ref` capture deferred. |
| **X5** | Function-value representation | 16-byte fat value `(code_ptr, env_ptr)`; refcounted env cell; non-capturing lambdas & plain `fun`s use `env_ptr = 0`; uniform calling convention. |

## 9. Implementation status

### v0.4.1 — methods & `impl` (landed)

Shipped end-to-end (lexer → parser → checker → interpreter → monomorphizer →
x86-64 codegen) with interpreter↔native parity and a negative corpus. Delivered
in three slices:

**v0.4.1a — inherent methods on `struct`/`enum`.** `impl T { … }` with
`self` / `var self` receivers; `recv.method(args)` resolution against a per-type
method table (D46, no UFCS); method-name coherence (unique per type, distinct
from fields, multiple blocks allowed); `var self` requires a mutable lvalue
receiver (D47) and may not rebind `self`. Each method lowers to a top-level
function with a synthesized `self` first parameter under a dotted, collision-free
name (`Point.sum`); the interpreter dispatches with `var self` write-back via the
actual receiver object (read-only `self` keeps value semantics). The native
backend needs **no** method-specific codegen: the monomorphizer rewrites
`recv.m(args)` into a plain call `m_lowered(recv, args)`, and since aggregates are
already passed by the address of the caller's storage, a `var self` method mutates
in place. (One fix: `_mut_addr_of_struct` now loads the pointer for an aggregate
*param*, so CoW pushes through `self.field` write back correctly.)

**v0.4.1b — generic `impl<T>`.** `impl<T> Box<T> { … }` (and multi-parameter
`impl<A, B> Pair<A, B>`); the impl's type parameters are inferred at the call site
from the receiver (and arguments), recorded on the call, and stamped per
instantiation by the monomorphizer like any generic function.

**v0.4.1c — methods on built-in types (no orphan rule, D45).** Read-only `self`
methods on concrete scalar / `str` / `StringBuilder` receivers, e.g.
`impl int { fun is_even(self) -> bool { … } }` then `(5).double().is_even()`.
*Deferred:* `var self` on built-ins and `impl`s on container builtins
(`[T]`/`[K: V]`/tuples), which need the lvalue-writeback / generic-builtin
machinery.

Surface: `examples/methods.my` (+ `#test` cases), parity programs in the burn
suite (`methods_*`), unit tests (`tests/unit/test_methods.py`), and a negative
corpus (`examples/errors/{type_method_unknown, type_var_self_immutable,
type_var_self_temporary, type_method_duplicate, type_method_field_collision,
parse_method_no_self, type_reassign_self, type_var_self_on_builtin,
type_impl_concrete_generic}.my`).

Deferred to later v0.4 phases: pipelines (v0.4.3), traits + operator
overloading + `#derive(Eq)` (v0.4.4).

### v0.4.2 — function types, lambdas & closures (landed)

Shipped end-to-end (lexer → parser → checker → interpreter → monomorphizer →
x86-64 codegen) with interpreter↔native parity, a negative corpus, and an
arena-reclaim stress test.

**Surface.** Function types `(T0, T1, …) -> R` and lambdas `(p: T, …) => expr`
or `(p: T, …) => { … }`. Lambda parameter types may be omitted when the expected
type is known from context (binding annotation, argument position, return type);
the block-bodied return type is inferred from its `return`s when not annotated.
Plain top-level (non-generic) `fun` names are first-class values that adopt the
matching function type. Function values can be passed, returned, stored in
`struct` fields / lists / maps, and called indirectly (`f(args)`, `a.f(args)`,
`xs[i](args)`).

**Capture (X4/D14/D48).** By-value snapshot at closure creation; mutating a
captured variable inside the lambda affects only the copy, and later mutation of
the original is invisible to the closure. Captured heap values
(lists/maps/strings/builders/recursive enums) are retained by the closure's
environment, so a captured snapshot is deep-immutable even as the original is
mutated through copy-on-write.

**Representation (X5).** A function value is a 16-byte fat value
`(code_ptr, env_ptr)`. Capturing lambdas allocate a refcounted environment cell
`[refcount][drop_fn][captures…]`; non-capturing lambdas and plain-`fun` values
use `env_ptr = 0`. Each lambda is lifted to a uniquely-named top-level function
whose hidden first parameter is the environment pointer; a per-lambda
`_env_drop` helper releases owned captures at refcount zero. Plain `fun`s used as
values get an `_fnval` thunk that ignores the (null) environment so every call
site uses one uniform closure calling convention. The native backend treats
`FuncType` as a by-address aggregate that owns heap, with null-safe
`__func_retain` / `__func_drop` runtime helpers managing the environment
refcount across copies, stores, and drops. Generic higher-order functions (e.g.
`compose<T>`) carry `FuncType` (and any lambda annotations naming a type
parameter) through monomorphization and are stamped per instantiation.

A fix that fell out of closures: `push`/`append`/`append_byte`/`remove` no
longer drop their value argument's temporary themselves — the enclosing
statement's `_drop_expr_temps` already does, and the duplicate drop double-freed
an owning temporary (a closure environment, or a list/map pushed inline),
letting the LIFO allocator alias freed cells.

Surface: `examples/closures.my` (+ `#test` cases), parity programs in the burn
suite (`closures_higher_order`, `closure_captures_list_deep_immutable`, and the
`closure_environment_reference_counting_reclaims_heap` arena-reclaim stress),
unit coverage of function-as-value typing in `tests/unit/test_types.py`, and a
negative corpus (`examples/errors/{type_call_non_function,
type_fn_arg_type_mismatch, type_lambda_arity_mismatch, type_fn_type_mismatch}.my`).

Deferred to later v0.4 phases: traits + operator overloading + `#derive(Eq)`
(v0.4.4).

### v0.4.3 — pipelines, composition & partial application (landed)

Pure desugaring over v0.4.2 lambdas/calls — **no new runtime**. Shipped
end-to-end with interpreter↔native parity, a negative corpus, and an
arena-reclaim stress test.

**Surface (X6/X7, D24).**

- **Pipeline `|>`** — `x |> f` ≡ `f(x)` and `x |> f(a, b)` ≡ `f(x, a, b)`: the
  left operand is spliced as the call's **first argument**. `|>` is the new
  loosest binary operator (below `||`), left-associative, and a new `|>` token.
- **Composition `>>`** — operand-typed (D24): when both operands are function
  values, `a >> b` ≡ `(x) => b(a(x))` (left-to-right), requiring `a: (A) -> B`,
  `b: (B) -> C` and yielding `(A) -> C`; when both are integers it is the v0.3
  right shift; a mix is a type error. The parser keeps `>>` at shift precedence
  (still lexed as two adjacent `>`), and the checker reinterprets it by type.
- **Partial application `_`** — a call carrying one or more `_` holes desugars to
  a lambda over the holes (left-to-right): `add(5, _)` ≡ `(b) => add(5, b)`,
  `div(_, 2)` ≡ `(a) => div(a, 2)`. Filled arguments are captured by value
  (inlined into the lambda body, then snapshotted by the v0.4.2 capture
  analysis). No implicit currying — every argument position must be present, so
  a missing argument without `_` is still an arity error. Holes also work in
  method calls (`obj.scale(2, _)` captures the receiver) and on function values.
  A bare `_` outside call-argument position is rejected.

**Where it happens.** `|>` is lowered in the **parser** (purely syntactic).
`>>` composition and `_` partial application are lowered in the **checker**,
which records the synthesized lambda on the node's `desugared` attribute; the
same post-check pass that rewrites `?` (`ast.Try`) into a `match` then replaces
these nodes with their lambdas, so the interpreter, monomorphizer, and x86-64
backend only ever see ordinary v0.4.2 lambdas and calls (the desugared closures
are reference-counted exactly like hand-written ones). The synthesized lambda
parameters carry explicit type annotations (rendered from the resolved callee /
operand types) so the monomorphizer's re-check resolves them without the
contextual hints that were only available during the first check.

Surface: `examples/pipelines.my` (+ `#test` cases), parity programs in the burn
suite (`pipelines_compose_partial`, `compose_partial_capture`, and the
`partial_and_compose_reference_counting_reclaims_heap` arena-reclaim stress),
unit coverage in `tests/unit/test_parser.py` and `tests/unit/test_types.py`, and
a negative corpus (`examples/errors/{type_hole_outside_call,
type_pipe_non_callable, type_compose_type_mismatch, type_compose_non_function,
type_partial_arity}.my`).

Deferred to later v0.4 phases: traits + operator overloading + `#derive(Eq)`
(v0.4.4).

### v0.4.4 — traits + operator overloading + derivable `Eq` (landed)

A **minimal** trait system on top of v0.4.1 methods, shipped end-to-end (lexer →
parser → checker → interpreter → monomorphizer → x86-64 codegen) with
interpreter↔native parity, a negative corpus, and an arena-reclaim stress test.
Most of it is **desugaring**: a trait impl is just a per-type method set, and
`a OP b` lowers to a method call — so the backends gained almost no new machinery
(the only runtime addition is operator dispatch on a *generic* value).

**Traits & `impl Trait for T` (D52, §4.1).** A `trait` (new keyword) is a set of
method *signatures* with `self`/`var self` receivers; `Self` denotes the
implementing type (a `SelfType` placeholder, substituted at conformance time).
`impl Trait for T { … }` provides them for any user or built-in `T` (no orphan
rule). The checker verifies the impl covers **exactly** the trait's signatures
(no missing, no extra) with matching receiver mutability and `Self`-substituted
parameter/return types, and enforces coherence: at most one **user** impl per
`(Trait, T)` pair. Trait methods join `T`'s per-type method table, so they
dispatch through the v0.4.1 `recv.method(args)` path with **no** new backend
code — a trait impl is registered, lowered, and monomorphized exactly like an
inherent method.

**Built-in operator traits (X8, §4.2).** A fixed set —
`Add/Sub/Mul/Div/Rem/Eq/Ord` — backs the overloadable operators. `a OP b`
desugars **uniformly** to the trait method on the operand type: `+ - * / %` →
`add`/…(`Self`-returning), `== !=` → `eq` (negated for `!=`), `< <= > >=` →
`cmp(…) OP 0`. The checker records the synthesized method call on the node's
`desugared` attribute and the existing post-check pass rewrites it away, so the
interpreter, monomorphizer, and codegen only ever see ordinary method calls.
**Primitives keep their built-in operators** (the desugaring fires only for
struct/enum operands), so there is no runtime cost when nothing is overloaded;
`Eq`/`Ord` lift the v0.2 D37 restriction for the types that implement them while
primitives keep their hardwired comparisons. Both operands must share the type
(D4). (Overriding a *primitive's* operators and tuple equality stay out of this
cut.)

**Derivable structural `Eq` (X8, §4.3).** `#derive(Eq)` on a concrete
`struct`/`enum` synthesizes an `impl Eq for T` whose `eq` is structural —
field-by-field for a struct, a `match (self, other)` over variant/payload for an
enum — written **in terms of `==` on the components**, so it reuses the operator
desugaring and requires each component to itself be `Eq` (an un-`Eq` field is a
compile error). Because it lowers to a normal method, the backends need no
derive-specific support. The allow-list is **`Eq` only** (Ord is the planned next
addition); deriving on generic types is deferred.

**Limited generic bounds (X9, §4.4).** A type parameter may carry built-in-trait
bounds, `<T: Add>` or `<T: A + B>` (on functions, methods, and impls). Inside a
bounded body the operators named by the bound are usable on a `T` value; the
operator is **not** desugared there (the type is still abstract). Bounds are
verified at the **call site** during the first type-check — the concrete type
argument (or, for a forwarded type parameter, the caller's own bound) must
satisfy each trait — so an unsatisfied bound is a compile error, never a runtime
one. The two backends then diverge as usual: the **interpreter** erases generics
and dispatches the bounded operator at runtime on the actual value
(struct/enum → its trait method; primitives → built-in), while the
**monomorphizer** specializes the body and lowers the now-concrete operator to
the resolved method call (mirroring its method-call lowering), so codegen sees
only plain calls. (A re-emitted `#derive`d struct drops its attribute in the
monomorphized program — the derived `eq` is already a concrete function, and
re-deriving could no longer see user impls that monomorphization dropped.)

**Where it happens.** `trait`/`impl Trait for T`/bounds parse in the
**parser**; the trait registry, built-in operator traits, conformance/coherence,
`#derive` synthesis, operator desugaring, and call-site bound checking live in
the **checker**; the **interpreter** adds runtime operator dispatch for the
erased-generic case; the **monomorphizer** lowers bounded operators to method
calls and strips lowered `#derive` attributes. Codegen is untouched.

Surface: `examples/traits.my` (+ `#test` cases), parity programs in the burn
suite (`traits_operators_derive`, `trait_generic_bounds`, and the
`trait_dispatch_reference_counting_reclaims_heap` arena-reclaim stress),
`tests/unit/test_traits.py`, and a negative corpus
(`examples/errors/{type_trait_unknown, type_trait_missing_method,
type_trait_sig_mismatch, type_trait_duplicate_impl, type_self_outside_trait,
type_builtin_trait_redeclare, type_operator_no_eq, type_derive_non_eq_field,
type_derive_unknown_trait, type_bound_unsatisfied, type_bound_unknown_trait,
parse_struct_type_param_bound}.my`).

This completes the v0.4 abstraction milestone. Deferred to v0.5+: trait objects,
default trait methods, user-defined trait bounds, deriving `Ord`/others,
`var self`/generic impls on built-in containers, and `ref` captures.
