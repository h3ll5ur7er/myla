## Tasks and the wiki

This repository uses [Genbeya](https://github.com/genbeya/genbeya): the board is `tasks/`, the wiki is `docs/`, settings are in `.genbeya.yml`. Both are plain Markdown and can be edited with any editor; Genbeya shows them as a board and a wiki with live references.

- One file per task, named after its ID (`MYLA-12.md`), in the epic folder of its component: `Python toolchain` (history: the toolchain retired by D101), `Self-hosted compiler`, `IR`, `Concurrency`, `Backends and platforms`, `Editor tooling`, `Tooling in Myla`, `Project tool`, `Documentation and repository`, `Rust edition` (history), and `Roadmap ideas` for larger directions.
- Workflow: `backlog` → `todo` → `in-progress` → `review` → `done`. Confirmed bugs that should be fixed next are in `todo`, everything else waits in `backlog`. An agent moves a task it has finished to `review`; only the owner moves tasks to `done`, or asks for it explicitly.
- A finished task records what proves it under one heading, `## Evidence`.
- One pull request per theme (an epic step or a review round), named after its tasks.
- The seeds are updated only when they can no longer bootstrap the sources (D207, [[Development/Bootstrap]]): a commit of the compiler's side, a `Stage:` commit with `scripts/update-seed.sh`'s seeds, then the use of what the seed didn't know. A change to `lib/std/` commits `selfhost/embedded_std.my`, which the bootstrap writes. CI checks the pull request's tip.
- After changing a module of `lib/std/`, run `build/myla test lib/std/<module>.my --stdlib lib`: a program reads the bodies of the modules of `std` it imports, the implicit ones (`std.str`, `std.char`, `std.int`, `std.list`, `std.option`, `std.map`, `std.hash`) too, only once it calls them (D179, [[MYLA-413]]; all but std.rt), so a broken body nothing calls passes every other run, the bootstrap included; `tests.burn.test_std_modules` checks each module whole as its entry. `scripts/update-seed.sh` checks every module of `lib/std` whole and stops on one that doesn't ([[MYLA-416]], [[MYLA-552]]).
- A new task takes the next free number across all epics. Abandoned tasks move to `done` with a note; tasks are never deleted.
- Reference tasks, pages and files with `[[MYLA-12]]`, `[[Language/Types]]` and `[[selfhost/checker.my#L10-L20]]`; `![[file#L1-L9]]` on its own line embeds lines.
- Name the task in commit messages and pull requests: `MYLA-12: Encode interpreter strings with surrogateescape`.
- Coding agents learn this from the `genbeya` skill (`.claude/skills/genbeya/`, `.agents/skills/genbeya/`) and the block in `AGENTS.md`. Those files are generated by Genbeya; refresh them from **Settings → AI agents** rather than editing them.
- Durable knowledge (how something works, why it was decided) goes into the wiki; keep pages current instead of adding new ones that contradict old ones.
- Myla code in the wiki and the README is tested (D114, [[MYLA-233]], `tests/burn/test_doc_blocks.py`). A ```` ```myla ```` block is a whole program:
  - It must type-check.
  - A block with a `main` must run with exit status 0, in the interpreter and natively alike, in an empty directory with empty input.
  - It may end with what it prints: a line `// output:`, then one `// ` line for each printed line (`//` for an empty one).
  - Write ```` ```myla fragment ```` for pieces of a program (signatures, statements, code that uses types defined elsewhere): they are not checked.
  - Write ```` ```myla error ```` for code that is meant to be rejected: it must fail to check.
  - Other code (shell, EBNF, assembly) uses its own info string.

## Agent skills

- `genbeya` (generated by Genbeya): how to use the tasks and the wiki.
- `myla` (`.claude/skills/myla/SKILL.md`, mirrored in `.agents/skills/myla/`): the language as agents need it, with the Rust and Swift habits that are wrong in Myla. Its `reference/` files, read from the code ([[MYLA-581]]), are the lookup for the syntax, the builtins and type rules, the standard library's API, the toolchain, and the compiler's internals with the checklist for adding a language feature. Keep it in step with the code like the wiki: a change to the language, a builtin, a std module's API or a tool updates the page or reference file that describes it. Keep both copies identical; its `myla` blocks are doc blocks (`test_doc_blocks.py` runs them and compares the copies), and new rows are checked with `build/myla check`.

## Working agreement for programming tasks

1. **Tests first where it makes sense (soft TDD).** Before changing behaviour, write the test that shows the bug or pins the new feature, and see it fail for the right reason. Refactorings rely on the existing tests; pure documentation needs none.
2. **Self-review before calling it done.** Read your whole diff again and look for what could be simpler, clearer, better named, better tested or better documented. Fix what you find, and rerun the tests.
3. **Show evidence.** When reporting the result, include concrete proof where it applies: test runs (before: failing, after: passing), measurements before and after, the output of the program or tool, the bootstrap's fixed-point check.

## Every function has tests

Every value-returning function in `examples/` carries `#test(args)[expected]` cases (the burn tests enforce it; in `selfhost/` the target is at least 80 % of them, reported and softly enforced: a warning, not a failure, D109, [[MYLA-184]]), so each file is its own regression suite (`myla test file.my`). Entry points and functions without a result are exempt. `test_examples_tests.py` enforces this for the examples.

## Regression corpus

Every language feature appears in at least one runnable example, and every known edge case, past bug and intentional error is captured by a program:

- accepted programs: `examples/*.my` (pinned output, native parity), `examples/regressions.my`, or a case in `test_compiler_parity.py`;
- rejected programs: one file per diagnostic in `examples/errors/`, with a `//~ <stage> error: <text>` directive ([[Development/Testing]]).

## Parity

The language is defined by its reference documentation, [[Language]] and [[Project/Decisions]]; the self-hosted toolchain is its implementation. Its interpreter (`myla run`) and its native code must print the same for every program: when they differ, one of them is wrong; fix the one that disagrees with the documentation and say so in the commit. What the tests hold the toolchain to, since the Python toolchain was retired ([[MYLA-219]], [[MYLA-288]]):

- **Native code and the other targets:** the self-hosted interpreter's output for the same program, and, for the examples, a hard expectation both are held to (`test_examples_run.EXPECTED`).
- **Diagnostics:** hard expectations: the error corpus's `//~` directives and, for a file the recordings don't cover, its whole rendered diagnostic in a sibling `.stderr` file (`TestPinnedDiagnostics`); a test's own `assertIn` of a message.
- **The recorded answers** of the retired toolchain ([[Development/Testing#recorded-answers]]) still check the files they cover, the examples as they were at the retirement (`RECORDED_EXAMPLES`) and the recorded snippets; nothing new is held to them, and they shrink as those files change.

## Decisions

Language and design decisions are numbered (D1 onwards) and recorded with date, decision and reason on [[Project/Decisions]]. Revisiting one is a new decision, not an edit.

## Style

- Python (the tests and scripts): standard library only, type hints, docstrings that explain why.
- Myla: `snake_case` values and functions, `PascalCase` types, four-space indentation, braces on the same line.
- A module of `lib/std/` uses the library's function rather than a private copy of it ([[MYLA-376]], [[MYLA-428]]). A copy stays, with a comment saying why, where it behaves differently, where the import would cost every importer check time for little (std.encoding: 1.4 to 1.8 M instructions, 0.3 ms (2026-11-12, `cc93cbd`), a program importing std.fs 3.4 % more, with the lazy modules of November 2026, [[MYLA-553]]; a copy only the tests call costs an importer nothing, as an unused function's body isn't checked), or where the library's version is slower on a hot path. Only a function of the caller's own module is inlined (the file that declares the caller, a built-in type's method included: [[MYLA-526]]), so a per-byte test or digit from another module (std.char's `is_digit`, `to_digit`) is a call each: it made `parse_uint64` 70 % slower, `percent_decode` 29 % and the formatting of a spec 2 to 3 %. Measure before swapping one in a loop.
- A timing is a comparison or is pinned (D197): a measured time, in a comment, a wiki page or a task, is either compared with another ("C 10 s, Myla 20 s"; "12 ms before the change, 7 ms after") or carries the date and the git hash it was measured at, `(2026-11-13, 748f3c2)`. A comment avoids timings where its reason stands without one; a benchmark page keeps its timings, compared or pinned.
- Commit and push work on a branch; keep generated files (`build/`, `.venv/`, `__pycache__`) out of version control.
