## Tasks and the wiki

This repository uses [Genbeya](https://github.com/genbeya/genbeya): the board is `tasks/`, the wiki is `docs/`, settings are in `.genbeya.yml`. Both are plain Markdown and can be edited with any editor; Genbeya shows them as a board and a wiki with live references.

- One file per task, named after its ID (`MYLA-12.md`), in the epic folder of its component: `Python toolchain` (history: the toolchain retired by D101), `Self-hosted compiler`, `IR`, `Concurrency`, `LLVM and platforms`, `Editor tooling`, `Tooling in Myla`, `Project tool`, `Documentation and repository`, `Rust edition` (history), and `Roadmap ideas` for larger directions.
- Workflow: `backlog` → `todo` → `in-progress` → `review` → `done`. Confirmed bugs that should be fixed next are in `todo`, everything else waits in `backlog`. An agent moves a task it has finished to `review`; only the owner moves tasks to `done`, or asks for it explicitly.
- A finished task records what proves it under one heading, `## Evidence`.
- One pull request per theme (an epic step or a review round), named after its tasks.
- A change to the compiler's output (`selfhost/`, `lib/std/`) comes with a new seed: `scripts/update-seed.sh`, then commit `bootstrap/seed.s` ([[Development/Bootstrap]]); CI checks it.
- A new task takes the next free number across all epics. Abandoned tasks move to `done` with a note; tasks are never deleted.
- Reference tasks, pages and files with `[[MYLA-12]]`, `[[Language/Types]]` and `[[selfhost/checker.my#L10-L20]]`; `![[file#L1-L9]]` on its own line embeds lines.
- Name the task in commit messages and pull requests: `MYLA-12: Encode interpreter strings with surrogateescape`.
- Coding agents learn this from the `genbeya` skill (`.claude/skills/genbeya/`, `.agents/skills/genbeya/`) and the block in `AGENTS.md`. Those files are generated by Genbeya; refresh them from **Settings → AI agents** rather than editing them.
- Durable knowledge (how something works, why it was decided) goes into the wiki; keep pages current instead of adding new ones that contradict old ones.

## Agent skills

- `genbeya` (generated by Genbeya): how to use the tasks and the wiki.
- `myla` (`.claude/skills/myla/SKILL.md`, mirrored in `.agents/skills/myla/`): the language as agents need it, with the Rust and Swift habits that are wrong in Myla. Keep it in step with the language like the wiki, and keep both copies identical; check new rows with `build/myla check`.

## Working agreement for programming tasks

1. **Tests first where it makes sense (soft TDD).** Before changing behaviour, write the test that shows the bug or pins the new feature, and see it fail for the right reason. Refactorings rely on the existing tests; pure documentation needs none.
2. **Self-review before calling it done.** Read your whole diff again and look for what could be simpler, clearer, better named, better tested or better documented. Fix what you find, and rerun the tests.
3. **Show evidence.** When reporting the result, include concrete proof where it applies: test runs (before: failing, after: passing), measurements before and after, the output of the program or tool, the bootstrap's fixed-point check.

## Every function has tests

Every value-returning function in `examples/` carries `#test(args)[expected]` cases (the burn tests enforce it; in `selfhost/` the target is at least 80 % of them, reported and softly enforced: a warning, not a failure, D109, [[MYLA-184]]), so each file is its own regression suite (`myla test file.my`). Entry points and functions without a result are exempt. `test_examples_tests.py` enforces this for the examples.

## Regression corpus

Every language feature appears in at least one runnable example, and every known edge case, past bug and intentional error is captured by a program:

- accepted programs: `examples/*.my` (pinned output, native parity), `examples/regressions.my`, or a case in `test_compiler_parity.py`;
- rejected programs: one file per diagnostic in `examples/errors/`, with a `//~ <stage> error: <text>` directive ([[Development/Testing]]).

## Parity

The language is defined by its reference documentation, [[Language]] and [[Project/Decisions]]; the self-hosted toolchain is its implementation. Its interpreter (`myla run`) and its native code must print the same for every program: when they differ, one of them is wrong; fix the one that disagrees with the documentation and say so in the commit. The burn tests also compare the lexer, parser, checker, interpreter and native code with the answers the retired Python toolchain gave, recorded before it was removed ([[Development/Testing]]).

## Decisions

Language and design decisions are numbered (D1–D116 so far) and recorded with date, decision and reason on [[Project/Decisions]]. Revisiting one is a new decision, not an edit.

## Style

- Python (the tests and scripts): standard library only, type hints, docstrings that explain why.
- Myla: `snake_case` values and functions, `PascalCase` types, four-space indentation, braces on the same line.
- Commit and push work on a branch; keep generated files (`build/`, `.venv/`, `__pycache__`) out of version control.
