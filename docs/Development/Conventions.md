## Tasks and the wiki

This repository uses [Genbeya](https://github.com/genbeya/genbeya): the board is `tasks/`, the wiki is `docs/`, settings are in `.genbeya.yml`. Both are plain Markdown and can be edited with any editor; Genbeya shows them as a board and a wiki with live references.

- One file per task, named after its ID (`MYLA-12.md`), in the epic folder of its component: `Python toolchain`, `Self-hosted compiler`, `Editor tooling`, `Documentation and repository`, and `Roadmap ideas` for larger directions that aren't designed yet.
- Workflow: `backlog` → `todo` → `in-progress` → `review` → `done`. Confirmed bugs that should be fixed next are in `todo`, everything else waits in `backlog`.
- A new task takes the next free number across all epics. Abandoned tasks move to `done` with a note; tasks are never deleted.
- Reference tasks, pages and files with `[[MYLA-12]]`, `[[Language/Types]]` and `[[src/myla/types.py#L10-L20]]`; `![[file#L1-L9]]` on its own line embeds lines.
- Name the task in commit messages and pull requests: `MYLA-12: Encode interpreter strings with surrogateescape`.
- Coding agents learn this from the `genbeya` skill (`.claude/skills/genbeya/`, `.agents/skills/genbeya/`) and the block in `AGENTS.md`. Those files are generated by Genbeya; refresh them from **Settings → AI agents** rather than editing them.
- Durable knowledge (how something works, why it was decided) goes into the wiki; keep pages current instead of adding new ones that contradict old ones.

## Agent skills

- `genbeya` (generated by Genbeya): how to use the tasks and the wiki.
- `myla` (`.claude/skills/myla/SKILL.md`, mirrored in `.agents/skills/myla/`): the language as agents need it, with the Rust and Swift habits that are wrong in Myla. Keep it in step with the language like the wiki, and keep both copies identical; check new rows with `myla check`.

## Working agreement for programming tasks

1. **Tests first where it makes sense (soft TDD).** Before changing behaviour, write the test that shows the bug or pins the new feature, and see it fail for the right reason. Refactorings rely on the existing tests; pure documentation needs none.
2. **Self-review before calling it done.** Read your whole diff again and look for what could be simpler, clearer, better named, better tested or better documented. Fix what you find, and rerun the tests.
3. **Show evidence.** When reporting the result, include concrete proof where it applies: test runs (before: failing, after: passing), measurements before and after, the output of the program or tool, the bootstrap's fixed-point check.

## Every function has tests

Every value-returning function in `examples/` and `selfhost/` carries `#test(args)[expected]` cases, so each file is its own regression suite (`myla test file.my`). Entry points and functions without a result are exempt. `test_examples_tests.py` enforces this for the examples.

## Regression corpus

Every language feature appears in at least one runnable example, and every known edge case, past bug and intentional error is captured by a program:

- accepted programs: `examples/*.my` (pinned output, native parity), `examples/regressions.my`, or a case in `test_compiler_parity.py`;
- rejected programs: one file per diagnostic in `examples/errors/`, with a `//~ <stage> error: <text>` directive ([[Development/Testing]]).

## Parity

The interpreter defines the semantics. A native backend that prints something else is wrong, unless the interpreter is (then fix the interpreter and say so in the commit). The self-hosted compiler must match the Python toolchain stage by stage.

## Decisions

Language and design decisions are numbered (D1–D58 so far) and recorded with date, decision and reason on [[Project/Decisions]]. Revisiting one is a new decision, not an edit.

## Style

- Python: standard library only, type hints, dataclasses for AST nodes, docstrings that explain why.
- Myla: `snake_case` values and functions, `PascalCase` types, four-space indentation, braces on the same line.
- Commit and push work on a branch; keep generated files (`build/`, `.venv/`, `__pycache__`) out of version control.
