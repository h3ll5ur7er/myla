# Testing

The tests are the burn tests in `tests/burn/`: modules of the standard library's `unittest` that drive the self-hosted toolchain, so they need nothing beyond Python, `as` and `ld` (gdb, node and the tree-sitter CLI for some, skipped without them). pytest runs them as well and is in the `dev` dependency group ([[MYLA-58]]). Python only runs the tests; it builds nothing. Until the Python toolchain was retired ([[MYLA-219]], D101) there were also unit and integration tests of it (`tests/unit/`, `tests/integration/`).

## Running

```bash
scripts/test.sh fast                                     # about a minute once the tools are cached (the quick burn modules; 2026-11-06, bae1a7f)
scripts/test.sh                                          # every burn test (all)
python3 -m unittest discover -s tests/burn -t .          # the same
python3 -m unittest tests.burn.test_error_corpus -v      # one file
uv run pytest tests/burn -q                              # pytest from the dev group
```

`scripts/test.sh fast` runs the burn tests without the self-hosting gates (`tests/burn/test_selfhost_*`) and every module of 4 s or more ([[MYLA-153]]); `test_aarch64` and `test_wasm`, which take minutes, are on its slow list); use it while working and the full run before committing.

### On another target

```bash
python3 scripts/test-target.py aarch64-linux             # the suites built for aarch64, run under qemu-aarch64 (about 2.5 min, 2026-11-05, `ea28e42`)
python3 scripts/test-target.py wasm32-wasi test_slices   # one suite, built for wasm32, run under Node
```

`scripts/test-target.py` runs the burn suites that build and run programs (the parity programs, the native runtime errors, the error corpus's runtime cases, the I/O suites and the language features) for another target ([[MYLA-268]]), one process per suite, as many at once as there are CPUs. It sets `MYLA_TEST_TARGET`, and `tests/burn/_native.py` then builds with `--target`, assembles with clang and `ld.lld` or `wasm-ld` (`assemble`) and runs under `qemu-aarch64 -0 <argv0>` or `node tools/wasm/run.mjs --argv0 <argv0>` (`run_argv`), so a test that builds through those helpers runs on the target unchanged. CI runs both targets (the `targets` job).

`tests/burn/_targets.py` is the one place that says which suites run and what each target is excused from, with the reason and its task: whole tests (`SKIP`, matched by id or a prefix of one) and single programs of a test's loop (`SKIP_PROGRAMS`, which the loop asks `program_excuse`). A test that reads the x86-64 assembly runs its program on every target and ends, skipped, where it starts reading (`_x86_only` in `test_selfhost_codegen.py`). An exception is for a real difference ([[Language/Targets]]) or a known gap with a task; check that it's earned by running the test with `MYLA_TEST_TARGET` set and the skip left out.

The burn tests build everything with the self-hosted compiler ([[MYLA-235]]). `tests/burn/_tools.py` bootstraps the compiler of the current sources from the seed (`bootstrap/seed.s` assembled is stage 0, it compiles the compiler, which compiles it again: at the fixed point the same as `build/stage3`, [[MYLA-218]]) and builds the self-hosted tools (`selfhost/<name>.my`) with it through `selfhost_tool(name)`, other Myla programs such as the grammar tool and the language server through `myla_tool(path, name)`, as `scripts/bootstrap.sh` does; `tests/burn/_native.py` builds the test programs with the natively built CLI (`myla build`). A tool is cached as `build/test-tools/<name>-selfhost-<hash>`, where the hash covers every source that can change it (`bootstrap/seed.s`, `lib/std/*.my`, `selfhost/*.my`, `tools/**/*.my`), so an edit to any of them rebuilds it and the stale copy is removed. The whole suite takes about 5 minutes in one process with the tools cached (1,035 tests in 313 s on 4 cores, measured on 2026-11-06 at `bae1a7f` with the aarch64 and wasm32 suites in it; 836 tests in 121 s on 2026-11-01 after [[MYLA-219]], at `850e6ae`); building the tools adds about a minute to a cold run (2026-11-01, `561fcc7`).

## Recorded answers

Until [[MYLA-219]] the burn tests compared the self-hosted toolchain with the Python toolchain, asking its lexer, parser, checker, loader, interpreter and CLI what a program's tokens, tree, errors, warnings and output are. Before it was removed, its answer to every question the tests asked was recorded into `tests/burn/data/golden/<name>.json.gz` (4.1 MB), and the functions that asked it, marked `@golden("name")` (`tests/burn/_golden.py`, whose docstring has the details), now answer from there. A question is keyed by the function and its arguments, a file in an argument standing for its content:

- A question about a changed file of `selfhost/`, `tools/` or `lib/std/`, which change all the time, is skipped when it has no answer; the skip count shows how much of that corpus has changed since the answers were recorded.
- Any other question without an answer (a new or changed example, a new snippet) fails, saying so: give that test an expectation of its own. The gates that ask about every example walk the examples of the retirement (`RECORDED_EXAMPLES` in `_golden.py`, the 32 of `backup/python-toolchain-final`), so a new example is held to `test_examples_run`'s expectation instead ([[MYLA-288]], [[MYLA-299]]).
- The repository's path and temporary directories are stored as placeholders, so a checkout elsewhere (CI) replays the same answers.

`MYLA_GOLDEN=record` records the answers again; it works only on a checkout that still has the Python toolchain, the branch `backup/python-toolchain-final` ([[Development/Bootstrap]]).

So the self-hosted interpreter and native code built by the self-hosted compiler are tested against each other and against the retired toolchain's answers: the interpreter gate compares `interp_main` with the Python interpreter's recorded output, and the native suites (`test_examples_compile.py`, `test_compiler_parity.py`, the runtime and I/O tests) compare binaries with it too. The 97 single-module programs the Python unit tests ran through the interpreter are kept, with what they printed and their exit status or runtime error, in `tests/burn/data/unit_programs.json`, and run in the self-hosted interpreter and natively (`test_unit_programs.py`). The comparisons with the Python backend's binaries went with it, as did the tests that only exercised the Python toolchain.

### Rewriting the recorded programs

A program the answers were recorded for can still be rewritten into a form that means the same, as [[MYLA-221]] moved the examples, docs and test programs from `push(xs, v)` to `xs.push(v)` (`scripts/to_methods.py`, token-based; it keeps every line where it was). The recordings survive it ([[MYLA-240]]):

- `tests/burn/data/golden/aliases/<name>.json.gz` (828 aliases, 135 KB) maps the key of a question about the rewritten texts to the recorded question's key, with the lines that changed and, for each, where every old column went. `_golden.py` answers the old question and moves the columns in the answer (rendered `--> file:L:C` and source lines with their carets, canonical diagnostics, the language server's positions, runtime-error tuples) to the new line. Lines don't move.
- The answers that are a program's structure (the lexer's tokens, the parser's tree) have no aliases: a rewritten program has other tokens. Their gates ask about copies of the files as they were recorded, `tests/burn/data/recorded_corpus/<path>` (30 examples), keyed by the original path.

To rewrite again: trace the questions on the old texts, rewrite, then build the aliases from the trace with the lexer the rewrite used (`LEX_MAIN`, kept from before any lexer change):

    MYLA_GOLDEN_TRACE=trace.jsonl python3 -m unittest discover -s tests/burn -t .
    git ls-files '*.my' '*.md' 'tests/burn/*.py' 'tests/burn/data/*.json' | grep -v recorded_corpus | xargs python3 scripts/to_methods.py
    python3 -m tests.burn.golden_aliases trace.jsonl

Restore the files that keep the old texts on purpose: the lexer and parser gates (`test_selfhost_lexer.py`, `test_selfhost_parser.py`), `_golden.py`, `golden_aliases.py` and `_continuation.py`. The builder checks that every traced key reproduces before it uses it. Compare a trace taken after the rewrite with the first: every oracle should get the same answers. A program that is about the old form (a test that the free function still works, a type error only the function form gives) stays as it was.

## What the Python tests covered

`tests/unit/` (627 tests) and `tests/integration/` (every example parses) tested the Python toolchain module by module; they went with it ([[MYLA-219]]). What they covered of the language survives as the 97 programs of `test_unit_programs.py` (see "Recorded answers"), the error corpus, the examples and the self-hosting gates. The language server's scenarios are in `tests/burn/_lsp_scenarios.py`, run by `tests/burn/test_lsp.py` (they also ran against the Python server until it was retired, [[MYLA-83]]).

## The error corpus

Every file in `examples/errors/` starts with a directive naming the stage that must reject it and a substring of the message:

```
//~ type error: cannot assign to an immutable binding
fun main() {
    let x = 1
    x = 2
}
```

Stages are `lex`, `parse`, `module`, `type` and `runtime`. A `module` case goes through the loader with the bundled standard library. A `runtime` case is also built natively, by the self-hosted compiler; it needs a second directive with the first line the native binary prints on stderr, which since D183 is the interpreter's text with its values ([[MYLA-415]], [[MYLA-441]]). The binary must exit with status 1 and print exactly that line and then the interpreter's position, `  --> <file>:<line>:<col>` ([[MYLA-65]]):

```
//~ runtime error: map key 2 not found
//~ native: runtime error: map key 2 not found
```

A file may also name the source text the diagnostic underlines, which pins the range an error reports ([[MYLA-65]]):

```
//~ type error: unknown function
//~ span: nope(1)
fun main() {
    let x = nope(1)
}
```

The stage must report exactly one error, unless the file says how many it reports; then it may name a substring of each later error's message, in order (D80, [[MYLA-65]]):

```
//~ parse error: expected variable name
//~ errors: 5
//~ next: expected an expression, found ')'
//~ next: expected ':', found 'int'
```

The first error's notes and help lines are named in order, each by its label and a substring of its message, and a note's underlined text may be pinned like the error's; a file without these directives expects an error without notes, so a note can't appear or change unnoticed (D83, [[MYLA-65]]):

```
//~ type error: cannot assign to an immutable binding
//~ note: 'x' is declared here
//~ note span: let x = 1
```

```
//~ type error: unknown name 'cuont'
//~ help: did you mean 'count'?
```

The diagnostics a file is checked against are the Python toolchain's, recorded ([[MYLA-219]], "Recorded answers"), and a file the recordings don't cover is held to its whole rendered diagnostic, carets and notes, pinned once in `<name>.stderr` beside it (`TestPinnedDiagnostics`, [[MYLA-288]]: 25 files on 2026-11-07); `MYLA_PIN_DIAGNOSTICS=1` writes a missing one, to be read before it is committed. The self-hosted CLI's diagnostic equals the recording on every recorded file. The corpus has 213 files: 12 lex, 11 parse, 2 module, 175 type, 13 runtime (the parse error for a method's trailing comma went with [[MYLA-225]]). The `type_recover_*` files have errors in declarations and bodies (D84, [[MYLA-110]]). More module errors (cycles, which file an error is attributed to) were covered by the Python loader's unit tests (`tests/unit/test_loader.py`, until [[MYLA-219]]); the codegen gate's `MODULE_ERRORS` and `test_packages.py` pin the self-hosted loader's.

## Generated `#test` cases

Most `#test` cases in `selfhost/` were generated by `scripts/harvest_tests.py` ([[MYLA-184]]), which ran the self-hosted CLI in the Python interpreter and was removed with it ([[MYLA-219]]; it is on the branch `backup/python-toolchain-final`). The self-hosted toolchain agreed with the Python one on the whole corpus and compiled itself to a fixed point, so what its functions returned then was a valid expected result, and a case protects it against regressions; the cases record behaviour, they don't specify it.

- `record` ran the self-hosted CLI over workloads (`check`, `build`, `test` and `run` of every example, `check` of the error corpus, REPL sessions, project commands, `fetch` from a local Git repository, `build -g`) and kept calls whose arguments and result print as Myla expressions, but none that did I/O.
- `generate` called the remaining functions: a parameter of a state type (the parser, checker, interpreter, code generator, lowering) or an AST type took a *factory* (`parser_on("1 + 2 * 3")`, `checker_on(…)`, …) over a set of one-line snippets; the other parameters took recorded values, or values of their type from a pool.
- `write` wrote the chosen cases above the functions that had none; `validate` ran both test runners on every module and removed each case either rejected, which is how differences between the two interpreters showed up ([[MYLA-238]]).

New cases are written by hand. The generated cases of path functions use `/work/myla` as the repository's path, so no checkout's path appears in them.

`scripts/test_coverage.py` reports the share of value-returning functions with cases per module; `tests/burn/test_selfhost_coverage.py` warns below 80 % (D109).

## Tests in Myla

Myla's own test system (D162, [[MYLA-303]]) is what the burn tests leave to the language: `#test(args)[expected]` cases and test functions (a bare `#test` on a function without parameters; `std.test` for the checks, `temp_dir()` for a scratch directory the runner removes), `[panic("…")]` and `[exit(n)]` for expected failures, `myla test --only <text>` and `--list` ([[Language/Attributes-and-testing#test-functions]]). A failed case unwinds its deferred blocks, so a test that makes files or starts processes cleans up however it ends; what it printed is shown under its FAIL line only. In a project, `myla test` also runs the test programs and the test files of `tests/` ([[MYLA-306]]), and `--native` (`--target <t>`) runs every case natively through a harness the compiler builds from the file ([[selfhost/harness.my]], [[MYLA-307]]): the file's text with a function per case appended, which calls the case's function with the case's arguments (their source text) and compares with the expected value through a structural equality and a repr generated per type, and a `#main` that runs the cases in child processes (`std.test`'s runner) and prints the interpreter's report. `tests/burn/test_test_functions.py` pins the report's every form, `test_test_native.py` holds the native report to the interpreter's on every example and standard library module with cases (the runtime, `lib/std/rt.my`, doesn't build as a program; the compiler's own modules were checked by hand, [[MYLA-307]]).

## Adding tests

- A new feature gets an example in `examples/` with `#test` cases, registered in `test_examples_run.py` and `test_examples_compile.py`.
- A fixed bug gets a program: an accepted one in `examples/regressions.my` (or a parity case in `test_compiler_parity.py`), a rejected one in `examples/errors/`. A test that asked the Python toolchain has no recorded answer for a new program and fails until it gets an expectation of its own ("Recorded answers").
- Anything the native backend does differently from the interpreter belongs in `test_compiler_parity.py`.
