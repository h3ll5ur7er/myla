# Decisions

The locked design decisions, newest first. They were made while the language was designed (June 2026) and are the "why" behind the rules on the [[Language]] pages. A decision is settled: changing one means adding a new numbered decision that supersedes it, not editing the old row.

Links in the table point at the design documents in [[Archive]], where each decision is discussed in detail.

## Adding a decision

| D83 | 2026-10-28 | **Notes and help lines on errors** ([[MYLA-65]], details: [[Architecture/Type-checker]], "Notes"). (1) An error carries a list of notes, each a `note` about a place in the error's file or a `help` line without a place; they are printed after the error, a note like an error (its `-->` and its line with carets), and both checkers give the same notes, compared by the checker gate through one canonical line per note after the error's. (2) The checkers add: where an immutable variable that is assigned to (or whose `var self` method is called) is declared; the first declaration a duplicate repeats; the return type a returned value doesn't match; and "did you mean" for unknown names, functions, types, fields and methods. (3) A suggestion is the closest candidate by optimal string alignment distance over UTF-8 bytes, if within a third of the name's length; ties go to the alphabetically first. (4) The error corpus names every note of an error (`//~ note:`, `//~ help:`, `//~ note span:`), so a file without them expects none | (1) A second place is what the messages that most need context lack (Rust and Swift show it the same way), and keeping notes in the error's file covers every case the checkers have: a function's variables, a module's declarations. Comparing notes like messages keeps the two checkers from drifting. (2) These are the questions a reader asks of those errors: "where did I declare it?", "which one was first?", "why is that type expected?", "what did I mean?". (3) Counting a swap as one edit catches the commonest typo; a third of the length is the limit Rust uses, and without a minimum of one edit, one- and two-letter names, where everything is close, get no noise. Bytes and a fixed tie-break make the choice independent of table order and identical in both checkers. (4) Messages and notes can then only change on purpose |
