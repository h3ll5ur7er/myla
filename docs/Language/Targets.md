# Targets

What a Myla program can count on wherever it runs, and what depends on the target it was built for ([[MYLA-266]]). `myla build` builds for the machine it runs on unless `--target` says otherwise (D127), and `myla run` interprets on the machine itself.

| Target | `--target` | What runs it |
| --- | --- | --- |
| Linux on x86-64 | `x86_64-linux` | The machine: a static executable, no libc |
| Linux on aarch64 | `aarch64-linux` | The machine (a Raspberry Pi 4 or 5 with a 64-bit OS, an ARM server): a static executable, no libc |
| WebAssembly on WASI preview 1 | `wasm32-wasi` | Node: `node tools/wasm/run.mjs`, or a web page through `tools/wasm/myla.mjs` (D125). Node is the host the suites test (D158); another WASI preview 1 host such as wasmtime should run the programs too, but nothing checks it |
| Windows on x86-64 | `x86_64-windows` | Windows: a static console `.exe` that imports only system DLLs, `kernel32.dll` and, where the program needs them, `bcrypt.dll` and the synch API set's DLL (D212, [[MYLA-722]]), cross-built on Linux (D214). The suites run it under Wine (D213), and CI's `windows` job on Windows itself what Wine can't show ([[MYLA-708]]); on a push to master it publishes that commit's `myla.exe` and `myla-lsp.exe` (D207). Its first step ([[MYLA-702]]) has the standard streams, the heap, the clocks, the arguments and the environment; the rest comes in steps and is `Unsupported` until then ([[MYLA-165]], D210, the last column below) |

## The same on every target

The language means the same everywhere, and the interpreter and every target print the same for a program that doesn't depend on what this page lists as differing:

- **Integers** wrap at their width; `MIN / -1` is `MIN` and `MIN % -1` is 0; shift amounts are masked at run time ([[Language/Expressions-and-operators]]).
- **Floats** follow IEEE 754 and print the same digits everywhere: the formatting is Myla code (`std.num`). A NaN prints as `nan`. Its sign and payload, which processors set differently, can't be seen: `std.math.to_bits` reads every NaN as `0x7FF8000000000000`, and `copysign` reads a NaN's sign as positive (D128).
- **`std.math`** gives bit-identical results everywhere: its functions are Myla code over the processor's correctly rounded `sqrt`.
- **Maps** iterate in insertion order (D105).
- **Runtime errors** print `runtime error: <message>` and the position, and exit with status 1 ([[Language/Attributes-and-testing]]). Running out of the stack is `runtime error: stack overflow` with status 1 on every target, without a position (MYLA-182, [[MYLA-261]]; on Windows from [[MYLA-703]], D216).
- **Text** is UTF-8: what a program prints is the same bytes on every target, `"\n"` a newline alone (no `\r\n` on Windows, whose console is switched to UTF-8 while the program runs), and its arguments and environment arrive as UTF-8 (D215).
- **`become`** passes six argument words freely on every target, and on the stack no more than the function received (D131, [[Language/Statements]]).
- **The order of tasks** on one worker is the defined order of D110. On several workers it is whatever the timing makes it; a program whose output depends on it is wrong.
- **Errors** are the same causes everywhere: `IoError` and `SpawnError` name `NotFound`, `PermissionDenied`, `AlreadyExists`, `IsADirectory` and the rest (D129, [[Language/Standard-library]]). Only `Other(code)` carries a platform's own number, which isn't portable.

## What a target can do

A program learns that its target lacks something from an error: the cause `Unsupported` (D129, D132). A platform module declares what its target lacks (`PROCESSES`, `SOCKETS` in `std.platform`, D209) and fails those functions with that cause instead of emulating them. Code chosen per target at compile time, for the standard library and packages, is still to come ([[MYLA-245]]).

## Sockets on another system

`std.net` never sees a file descriptor or a `sockaddr` ([[Language/Standard-library/Net#porting-sockets-to-another-system]]). A port, Windows' over Winsock next, gives `std.platform`'s socket functions again (`sock_open` to `sock_close`, `sock_poll`, `net_config`, and the poller's `poller_watch_socket`, `poller_forget_socket` and `poller_event_ready`, what an event is ready for, [[MYLA-518]]): each gives 0 or more or minus a cause code, its codes mapped onto std.ioerror's causes (`WSAECONNREFUSED` onto CONNECTION_REFUSED, `WSAEWOULDBLOCK` onto WOULD_BLOCK, or IN_PROGRESS for a connect, D209); addresses cross as a portable record; a socket starts blocking and is made non-blocking explicitly; data is sent and received, never read or written, and a socket has its own close. Readiness is 1 to receive or accept, 2 to send or a connect's end, an error or a hang-up both: `WSAPoll` for `sock_poll`, and for the reactor `WSAPoll` beside its wake-up event or IOCP. The hosts file's path and the name servers come from `net_config`, as Windows keeps both elsewhere.

## The terminal and signals on another system

`std.term` and `std.signal` never see an `ioctl`, a termios byte or a signal number beyond 2 and 15 ([[Language/Standard-library/Term#porting-to-another-system]], [[Language/Standard-library/Signal#porting-to-another-system]]). A port, Windows' over the console API next, gives `std.platform`'s `term_is_tty`, `term_size`, `term_get_mode`, `term_set_mode`, `term_make_raw`, `term_enable_vt`, `signal_listen` and `signal_take` again, each 0 or more or minus a cause code (NOT_A_TERMINAL for a stream that isn't a terminal). The descriptors 0 to 2 name the standard streams (`GetStdHandle`); being a terminal is `GetConsoleMode` succeeding; the size is the visible window of `GetConsoleScreenBufferInfo`, as columns times 65536 plus rows; a mode is an opaque block the port fills (the console mode) and gets back unread; raw mode clears line input, echo and processed input and sets `ENABLE_VIRTUAL_TERMINAL_INPUT`, so keys arrive as the escape sequences `parse_key` reads; `term_enable_vt` sets `ENABLE_VIRTUAL_TERMINAL_PROCESSING`. A signal comes through a handle the reactor waits on as on input, one byte each, 2 for an interrupt and 15 for termination: a `SetConsoleCtrlHandler` routine writes `CTRL_C_EVENT` and `CTRL_BREAK_EVENT` as 2 and `CTRL_CLOSE_EVENT`, `CTRL_LOGOFF_EVENT` and `CTRL_SHUTDOWN_EVENT` as 15 to a pipe, and nothing is installed until a program listens.

## Files and children on another system

`std.fs` and `std.process` see no `struct stat`, file descriptor table or `fork` ([[MYLA-378]], [[MYLA-363]]). A port, Windows' next, gives `std.platform`'s `path_stat(path, follow, out)` again: six words at `out`, the size, the kind (`KIND_FILE`, `KIND_DIR`, `KIND_SYMLINK`, … from the attributes, as wasm32 takes them from WASI's file type), the permission bits (POSIX's, from the read-only attribute: 0o444 or 0o666, 0o555 or 0o777 for a directory; D218), the modification time in nanoseconds since 1970, and a device and a file number that together name one file (the volume's serial number and the file index of `GetFileInformationByHandle`), a link followed or not (`FILE_FLAG_OPEN_REPARSE_POINT`); 0 or minus a cause code, its system's codes mapped onto std.ioerror's causes (`ERROR_FILE_NOT_FOUND` and `ERROR_PATH_NOT_FOUND` NOT_FOUND, `ERROR_ACCESS_DENIED` PERMISSION_DENIED, …, another OTHER plus its code, D219). A directory's entries are `dir_read` into records of its own (the names of `GetFileInformationByHandleEx`'s directory records as UTF-8, D215, [[MYLA-704]]) that `dir_entry_name`, `dir_entry_name_len`, `dir_entry_kind` and `dir_entry_size` read. Its `close(fd)` gives the close's result as one (`CloseHandle`). Windows' `spawn_piped(paths, argv, opts)` ([[MYLA-705]]) reads the three streams as `opts[1]`'s letters (`std.rt.spawn_piped`): `p` a pipe whose other end comes back in the result, `i` this process's, `n` the `NUL` device, and for the input `t` a text (a temporary file deleted on close, as Linux's `memfd`) or `d` a descriptor handed over, which `CreateProcessW` takes as the handles of `STARTUPINFO`; a stream that isn't a pipe is -1 in the result, the rest as Linux's (`[cause, pid, in, out, err, exited]`, `exited` the process's handle, which `poll_read` and the poller wait for). It looks for the program itself (std.rt hands the name over as it is): `PATH`'s entries are `;`-separated and each name tried with `PATHEXT`'s extensions. A child's status is its exit code's 32 bits, which `reap` gives whole and std.rt keeps as a run's for std.process (`__reap`'s own result is the low 8 bits, D216). Until its step a port has none of this: its `PROCESSES` is false and each fails with UNSUPPORTED, as wasm32's (D210). The string and builder primitives of [[MYLA-369]] are std.rt's own Myla and need nothing of a port.

## How each target is built

Every target runs the burn suites that build and run programs, x86-64 natively and the others under qemu-aarch64 and Node (`scripts/test-target.py`, [[Development/Testing]], [[MYLA-268]]); `myla test --target <t>` runs a file's or a project's own `#test` cases there the same way ([[Language/Attributes-and-testing#native-runs]], D162). What the others are excused from, and why, is in `tests/burn/_targets.py`: only what the table above lists (no processes on wasm32, one worker, Node's own memory measured), the tests that read x86-64 code, and the standard library's own cases under qemu-aarch64 (a qemu process per case: `std.int`'s 1826 take 4.6 minutes, 2026-11-09, `0d0c35e`); on wasm32 they run, every case ([[MYLA-370]]).

An implementation may leave out what only parallel workers need when only one worker can exist: the deep copies at task boundaries and the atomic counts of actor handles (D133). Values are immutable, so the difference shows only in speed. wasm32 leaves out both: a value crossing between tasks keeps its counts (an argument of a child, a capture of an async lambda, a result), and an actor handle's count is a plain one. A program handing a 20000-element list and a 200-entry map to 6000 children ran in 0.42 to 0.55 s instead of 0.62 to 0.69 s under Node (2026-11-05). The details of each target's code generation, runtime and platform layer are on [[Architecture/Native-backend]].
