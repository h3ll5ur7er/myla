# Self-hosted compiler

`selfhost/` is the Myla toolchain written in Myla: lexer, parser, checker, a code generator through the IR with backends for x86-64 and aarch64 Linux and wasm32 on WASI, a module loader, an interpreter and the CLI. It bootstraps from a committed seed, its own assembly, and compiles itself to a byte-identical fixed point ([[Development/Bootstrap]]). It was ported from the Python toolchain and tested against it, stage by stage; since that was retired (D101, [[MYLA-219]]) it is the only toolchain, and the tests compare it with the Python toolchain's recorded answers ([[Development/Testing]]).

## Writing a compiler in Myla

Myla has no global variables and no module-level maps, and everything is a value, which shapes the code:

- Symbol tables are lists of records searched with `while` loops (`StructInfo`, `EnumInfo`, `FuncSig`, `MethodEntry`, `TraitInfo` in the checker; `funcs`, `str_texts` in codegen).
- Scopes are lists of frames: `[Frame{names: [str], binds: [Binding]}]`.
- Maps serve as side tables keyed by node id (`resolved`) or by name (`const_strs`, `dbg_types`).
- `Type` is an enum: `TInt(width, signed) | TFloat | TChar | TBool | TStr | TSB | TStruct(name, args) | TEnum(name, args) | TTuple | TList | TMap | TFunc(params, Option<ret>) | TAsync(TFunc) | TParam | TSelf | TError`. An async function type wraps a `TFunc` (D89) rather than adding a flag to it, which would make every `Type` a word larger.
- Errors are `Result` values propagated with `?`: a type error is `CheckErr{line, col, sp, msg, decl}`, the declaration naming its file, `sp` the range of the node it is about (`terr_at(e.line, e.col, e.sp, …)`, where the Python checker raised `at=e`). The checker collects the first error of each function in `errs` once its tables are built (`run_all`, D80). The lexer and parser have no `Result` plumbing: the lexer records its first error (a `Diag` with its range) and skips to the end of the input; the parser keeps an error as pending and skips to the end of the input, where every loop ends, which unwinds the parse like Python's exception; a block, an impl or trait body and the program then record it, go back to where it was found and skip to the next statement, member or declaration (`recovered`, `sync`), exactly as the Python parser (`src/myla/parser.py`) did ([[Architecture/Lexer-and-parser]]). `parse_source_all` returns every parse error, `parse_source` the first; a `Report` carries the errors after it in `more`, and `diag.render` prints them all.
- Ranges are made the way the Python parser made them: `mk_expr` and friends give a node the range from its position to the end of the last token consumed (`span_from`), `mk_expr_from` from the token its left operand began with ([[Architecture/Lexer-and-parser]]). The loader keeps them when it rebuilds nodes.
- State lives in structs passed around with `var self` methods; updating a nested value means rebuilding it.

## Differences from the Python toolchain

How the self-hosted pipeline differed from the Python toolchain it was ported from, when that was retired ([[MYLA-219]]):

| Area | Python toolchain | Self-hosted |
| --- | --- | --- |
| Modules | Qualified names, privacy, packages | The same since [[MYLA-30]] (small differences on [[Architecture/Module-loader]]) |
| Monomorphization | Separate pass, then a second check | During code generation, with a substitution list |
| Floats | Full support | Full support since [[MYLA-29]]: literals converted with integer arithmetic (`std.num`, moved there from `selfhost/floatlit.my` in [[MYLA-79]]), the float runtime taken over from the Python backend's (generated from it by `scripts/gen_selfhost_runtime.py` until [[MYLA-219]], edited in `codegen.my` since) |
| Diagnostics | Messages with file positions and ranges | The same: lex, parse, module and type errors print exactly as in the Python CLI, file, source line and the underlined range included ([[MYLA-28]], [[MYLA-65]]) |
| Runtime errors | Messages | The interpreter (`myla run`/`test`): the same messages and rendering since [[MYLA-32]]; native binaries: `runtime error: <message>` and `  --> file:line:col` on stderr and exit 1, as the Python backend's ([[MYLA-17]], [[MYLA-65]]) |
| Heap | 1 GiB arena, size-class free lists (powers of two above 4 KiB since [[MYLA-80]]) | 16 MiB chunks mapped as needed (D106, [[MYLA-162]]; a 4 GiB arena before), size-class free lists (memory reused since [[MYLA-22]]); maps leave a tombstone on `remove` and then rebuild, the Python backend rebuilds directly ([[MYLA-18]]) |
| Closure environments | `[drop fn][captures…]`, captures retained and dropped | The same since [[MYLA-22]]; compositions and partial applications own their parts too |
| Stdlib root | Built in | Carried by the binary (`<myla>`, read from memory, [[MYLA-243]]), or `--stdlib <dir>` / `MYLA_STDLIB` |

The calling convention, value layouts, list/map/builder runtimes and the evaluation order are ported nearly line for line from [[Architecture/Native-backend]].

## How it was brought up

Each stage was ported and tested against the Python oracle before the next one (v0.6–v0.9):

1. **Lexer**: `myla tokenize --canonical` vs `lex_main`, byte for byte, on every example.
2. **Parser**: `myla parse --canonical` vs `parse_main`.
3. **Checker**: `myla check --canonical` vs `check_main`: same accept/reject and same error position on the examples and the error corpus.
4. **Code generator and loader**: native output of `gen_main`-compiled programs vs the interpreter.
5. **Fixed point**: the compiler compiles itself until the output stops changing.

The burn tests `tests/burn/test_selfhost_*.py` keep these gates, against the Python toolchain's recorded answers since it was retired. They build the self-hosted tools with the self-hosted compiler, bootstrapped from the seed, so they test self-compiled binaries as well as, through the programs `gen_main` compiles, its code generator and runtime (including the arena-reclaim stress programs, with a memory bound) ([[Development/Testing]]).

## Current state

- The three-stage fixed point holds: stage 2 and stage 3 output are identical (6.2 MB of assembly, 324,557 lines, on 2026-11-01); stage 3 compiles the compiler in 1.1 s with a 111 MB peak (earlier measurements, on another machine: 2.1 s and 94 MB with the old emission path; 1.8 s and 78 MB before nodes and tokens carried their source ranges, [[MYLA-65]]; 211 MB while strings were never freed, [[MYLA-18]]; 243 MB before match results and condition temporaries were released, [[MYLA-74]]; 359 MB while `free` was disabled, [[MYLA-22]]).
- Against the interpreter, native builds match on the 32 examples but `args`, which differs only in argv[0] (the binary's path instead of the source file's); the aarch64 and wasm builds match the x86-64 ones ([[Architecture/Native-backend]]).
- The stage 4 CLI's `myla run` (the Myla interpreter, compiled) printed byte for byte what the Python CLI printed (stdout, stderr, exit code) on all the examples and the whole error corpus: lex, parse, type and runtime errors ([[MYLA-28]], [[MYLA-32]]); the gates compare it with that recorded output. The program's `args()` is the file followed by the arguments after it, as under the Python `myla run`. Since [[MYLA-74]] it updates containers in place, so a loop of a million `push`es takes 4 s (the Python interpreter: 10 s).
- Further bugs: [[MYLA-23]] … [[MYLA-27]], [[MYLA-32]], [[MYLA-33]]. See [[Project/Known-issues]].
