# Module loader

Modules are a front-end concern only: [[selfhost/loader.my]] turns an entry file and its imports into one flat list of declarations (`Loaded`) whose top-level names are unique, and the checker, interpreter and compiler never see an import. The language rules are on [[Language/Modules]].

## Steps

`load_program_opts(entry, opts)` does them with `LoadOptions { stdlib_root, packages, root, overrides }` (the other entry points are below). Without packages and a root the loader behaves as before [[MYLA-92]]. `packages` is a list of (name, directory) pairs, the `--package name=dir` flags (`parse_package_flag` splits one); `root`, the project root, is the entry file's directory when it is empty.

0. **Packages.** The list is checked first: a package named `std`, a name that isn't an ASCII letter followed by ASCII letters, digits and `_` (or is a keyword), a name given twice, an empty or missing directory are module errors without a position.
1. **Load.** Starting from the entry file, read, lex and parse each module once (keyed by its normalized path), and follow its imports depth-first, resolving each once (the module keeps its imports' targets). Every module but the entry is lexed and parsed without its `#test` cases (`parse_source_with`, `skip_tests`: the lexer skips an attribute `#test(…)[…]` unlexed, over its brackets, strings, chars, f-strings and comments, [[MYLA-359]], and the parser skips any case it still meets, [[MYLA-396]]): only `myla test` of a module's own file runs its cases ([[MYLA-360]]), and std.int has 2,042, so a module of `std` may import it at no cost. A broken case in an imported module shows only when its own file is tested. The implicit modules (below) are read lazier still ([[MYLA-359]]): their files are known before the entry is loaded (`implicit_files`, `Loader.lazy`), so also where a program or a module imports one, and so are the other modules of `std` but the entry and std.rt (`lazy_std`, [[MYLA-413]], D179 (2); a program's own modules are read whole). Which files those are goes by the file's root, not its module id (`in_std_root`: under the stdlib root's `std/` or the carried library's): a program's `sub/std/helper.my` is read whole as the program's (a `std/` or `std.my` at the program's root, which would be named `std$helper` as the library's modules are, is refused at the import, `Loader.own_std`, D255), and `parse_module` parses them with `parse_source_lazy`, which leaves each function's and method's body unparsed (the lexer skips it, see [[Architecture/Lexer-and-parser]]) and keeps it as a site (`BodySite`: its place, its code points and node ids kept for it) beside the module's code points (`Module.sites`, `Module.cps`). `overrides` replaces a file's text with an in-memory buffer; the language server uses it for unsaved edits.
   - **The parse the toolchain carries** ([[MYLA-412]]). Such a module of `std` isn't lexed and parsed at all when its text is the one the toolchain was built with: `parse_module` asks `Loader.cached`, which finds the file's path under the stdlib root (`std/io.my`) and, when `stdroot.embedded_parse` says the text is the embedded file's (the same bytes: the built-in library, or a `--stdlib`/`MYLA_STDLIB` directory that holds the same file; an edited or another library, or an editor's buffer, is parsed as before), reads the parse kept beside it in `selfhost/embedded_std.my` (`embedded_cache`) with `astcache.decode`, its node ids moved to start at `next_id`. The parse is `parse_source_lazy`'s, written when the toolchain is built: `tools/embed/main.my`, which `scripts/bootstrap.sh` runs before stage 1 to write `embedded_std.my`, encodes each module of `std` but std.rt with `astcache.cache_entry` (the form is described at the top of [[selfhost/astcache.my]]: a string table and the declarations, numbers in printable digits, a node's id and line relative to the last one, a name the parser made of an id, `%for12`, relative to the module's first). The writer checks each entry before it keeps it: the parse at another first id is the same moved, the entry reads back as the parse, and each body read from its own text is the one read from the module's; else the module is carried without its parse (`embed` says so, and `stdroot`'s `carried_unparsed` case fails) and parsed on every use. With the parse comes, for each body left for later, where its text is in the file's bytes, so the loader keeps the module's text (`Module.src`, `Module.bytes`) instead of its code points, and decodes only the bodies it reads (`astcache.body_part`); the implicit modules' entries also hold their bodies parsed (`Bodies`, `cached_body`, which `LazyTable.read_parsed` takes before parsing the text), as every program reads some of them. A hello world's `myla check` went from 40.7 M to 20.9 M instructions (a program importing std.io 59.9 M to 36.4 M, std.http 200.6 M to 145.3 M). The parse is the one the toolchain's own parser gives only while `embedded_std.my` is current: `scripts/bootstrap.sh` rewrites it, and `test_embedded_std.py` fails when it isn't what `lib/` and the parser give; `tests/burn/test_std_cache.py` builds every example and the compiler with and without it.
   - **Implicit modules** ([[MYLA-320]], D164). Unless the entry file is a module of the standard library (`is_std_module`: under the root's `std/`, or with the embedded library under a copy of it on disk, D152's rule), `load_implicit` then loads each of `implicit_modules()` (`str`, `char`, `int`, `float`, `list`, `option`, `map`, `hash`) that the stdlib root has, `std/<name>.my` found by `descend` as an import of `std.<name>` would find it, and follows its imports; one the library doesn't have is skipped. std.float is loaded only for a program that may use it (D258, [[MYLA-796]]): `without_unused_float` drops it unless a module of the program, read as bytes by `may_call_method`, calls a method named as one of its own (`.sqrt(`, `. abs (`, `.max<`; `float_method_names`, which `test_float_methods` holds to `lib/std/float.my`) or has an impl on a float type (`impl float64`, for the duplicate of one of its names). Comments and strings count too, an f-string's holes hold calls, so the test errs on the side of loading. Without it a program loads neither std.float nor the std.math it imports: a hello world's `myla check` went from 25.49 M to 21.45 M instructions, its `myla run` from 28.96 M to 24.86 M (valgrind's count, the tools of `e659342` against this change, 2026-11-18). A method name std.int shares (`abs`, `min`, `max`, `pow`, `clamp`, `signum`) loads it for an integer's call too. No module's bindings get them; what they bring is their impls, whose methods need no binding. A module imported explicitly too is the same module, loaded once.
2. **Module ids.** The entry module's id is empty; every other module's id is its path, without `.my`, with every run of other characters replaced by `$`: relative to the stdlib root for the standard library (`std$io`), to a package's directory, after the package's name, for a package (`geo$shapes` for `G/shapes.my`, as if `G` were `geo/` in the project root, so no fetch path or commit appears in a name; the innermost directory wins if they nest), to the project root for the project (`geometry$geometry`), and above the project root with one `up` per level climbed (`up$up$selfhost$tokens`), so `../x.my` and `x.my` never share an id. The rules are `module_id`'s; the Python loader adopted them in [[MYLA-81]] (before, it dropped the `..` and named the standard library by its path from the project). Paths are compared as written, but for one case: an entry that is a module of the standard library named through another spelling of the root than `--stdlib`'s (a symbolic link) takes the root as the entry spells it (the driver's `own_library`: `std_tree_root` of the file, and `same_dir`, which compares the two directories' device and file number), so `myla test libcopy/std/option.my --stdlib liblink` tests std.option once, where it was a program's module beside the library's, 18 of its methods twice ([[MYLA-793]]). A program's own `std/` at its root is refused (D255), so its `std/rt.my` no longer collides with std.rt; one below the root is any module. Two paths that sanitise to the same id are an error.
3. **Exports.** A module exports its `pub` declarations as `("decl", "id$name")`; `pub from` and `pub import … as` re-exports are added in a loop until nothing changes, so chains of re-exports settle.
4. **Bindings.** For each module: its own declarations, plus what its imports bind, `("decl", qualified)` or `("module", id)`. A collision is a module error.
5. **Renaming.** `Renamer` walks every declaration and rebuilds each reference that resolves to a module-level name in its qualified form: type annotations, struct literal names, pattern type names, trait names, bounds and value references. It tracks local variable and type-parameter scopes so shadowed names stay untouched. A field chain whose prefix is a module binding (`geo.manhattan`, `a.b.c.f`) collapses into the qualified name. A dotted name in a type (`args.Spec`, D170), in an impl's trait or in a bound (`T: json.ToJson`, [[MYLA-398]]) is a module's exported type or trait (`module_type`).
6. **Merge.** All modules' declarations (minus imports) are concatenated into one list: the implicit modules first (`merge_order`), so that the checker registers their methods before a program's and a program's method of the same name on the same type is the duplicate, then the others in load order. The impls of the modules of `std` are recorded by node id with their module and file (`Loaded.std_impls`): the checker counts their methods as the standard library's code (a method on a built-in type is named after the type, `str.trim`, not `std$…`, so only its impl tells), and names the module and the place in the note of a duplicate method. The functions of every module of `std` but the entry are recorded too, with `lazy` set for all but std.rt's (and `implicit` for an implicit module's): the checker checks those bodies only once they are called ([[MYLA-359]], [[MYLA-413]]), and gives the library's privileges (raw memory, D152; `__` primitives without a warning, D100) to the functions and impls recorded, so by the file's root, not by a `std$` name (`Checker.in_std`, [[MYLA-584]]); the checker's few rules that go by a `std$` name, such as `exit` that never returns and `task.cancel`, hold as only the library's modules have such names (D255). std.rt is read whole, as the back ends call its functions by the primitives they replace; the other functions they call by name are on `backend_std_functions`, which the checker marks as called ([[MYLA-432]]). A native build's program has tasks (`Checker.task_line`, D90) where an `async let` is in any body loaded, read or not (`LazyTable.task_line`, `async_let_in`), so that it is built as when every body was read. The bodies their parse left (`LazyTable.add`, by `body_key`: the declaration's id, an impl's for a method, and the line and column of the body's `{`, whose limits the lexer tested, [[MYLA-416]]) go to the checker as `Loaded.bodies` (`LazyBodies`), whose `parse` reads one when the checker first checks it (`LazyTable.read`): `parse_body` lexes and parses its code points with the node ids kept for it, so its nodes are in its module's range of ids (`file_of` finds the file, a debugger the line), and the module's renamer, kept for it, renames it with the names in scope there, as `Renamer.function` would have (the parameters, `self` in an impl, the type parameters and `Self`). A lex, parse or module error of a body read so is reported where it is, with its kind (`kind_of`), when a program calls the function; one no program calls shows only in the module's own `myla test` or `myla check`, which parse the whole file, as its type errors do, and `scripts/update-seed.sh` checks every module of `std` so (D179, [[MYLA-552]]). When the entry file is itself a module of `std` (`myla test lib/std/task.my`), whose names stay unqualified as an entry's do, its functions are recorded too, with the module's dotted name (`std_module_name`): that is how the checker knows its `cancel` for `task.cancel` ([[MYLA-388]]).
   - **Reading every body at once** ([[MYLA-552]]). With `MYLA_EAGER_BODIES=1` (`eager_bodies`) the loader reads every body it left for later before the program is checked (`read_every_body`, through the same `LazyBodies.parse` the checker reads one with, so the node ids are the same), and the checker gets the declarations whole; they are still checked only once called (D179), and a body that doesn't read stays left, so its error is reported where the program calls it, as without the switch. It is the oracle of the lazy load: what is built must not depend on which bodies were read, and `tests/burn/test_lazy_std.py` (`EagerOracle`) builds the parity programs (x86-64 and aarch64) and the compiler both ways and compares the assembly. It found one dependency: the code generator's vote on owned parameters (`find_kept_params`, [[Architecture/IR]]) counted the calls in every body loaded, so a body read changed how the functions it calls were built (`packed_byte_lists`, its output equal); a body of `std` nothing called (`Checker.unmarked_std`) now neither votes nor keeps.

Path resolution (`resolve`) uses the leading-dot count: none means the project root, then the stdlib root; one dot the importer's directory; each further dot one level up. The last segment is a file `x.my` or a package `x/x.my`. Without dots the first segment decides: `std` resolves in the stdlib root only (the Python loader also reported a project `std` as an error, see below); a package's name in its directory only (`resolve_in_package`: `geo` is `G/geo.my`, `geo.b.c` is `G/b/c.my` or `G/b/c/c.my`), and a project `geo.my` or `geo/` is then an error, `'geo' is a dependency and cannot be shadowed by a project file or directory`, raised at the import like the `std` one; any other name in the project root, then the stdlib root ([[Language/Modules]]).

The standard library root is a directory (`--stdlib`, `MYLA_STDLIB`), or by default `<myla>`, the library the toolchain carries ([[MYLA-243]], [[selfhost/stdroot.my]]): its files `<myla>/std/io.my` are read from memory (`source_text`: an editor's buffer first, then an embedded file, then the disk), so resolving, module ids and diagnostics work the same as for a directory and no file is written on any platform.

## Copies for a target

`for_target(opts, t)` gives the options a native build or a harness loads a program with for the target `t` ([[MYLA-163]], [[MYLA-700]]): the target's platform module (`Target.platform_file`, `std/platform_windows.my`) is read for `std/platform.my`, from the library the tools carry and from the stdlib root, as `overrides`. A module may have a copy for a target too, its name ending as the target record's `copies` says (`std/path_windows.my` beside `std/platform_windows.my`, [[MYLA-704]]; the modules are `copied_modules()`'s): `own_copy` takes it for `std/path.my` where there is one, and leaves a module the caller gives a text of its own (a test harness built of it), so `myla test lib/std/path.my --target x86_64-windows` runs that module's cases. Windows has three: `path_windows.my` (std.path on Windows' paths, D215), `path_style_windows.my` (std.path_style's one constant, `WINDOWS`, which std.fs and std.glob read) and `system_error_windows.my` (std.system_error's `error_text`, the words for Windows' error codes that std.rt and std.io give a failed write, [[MYLA-716]]; its import costs checking a program that imports std.io 48.6 M → 49.2 M instructions, valgrind's count with this branch's tools and the library copied out of the repository, io.my with and without it, 2026-11-16). aarch64 Linux has one, `linux_calls_aarch64.my` (std.linux_calls, the system calls' numbers and the layouts Linux's one std.platform reads, [[MYLA-758]]), and no platform module of its own (`platform_file` ""): its import made a hello world's `myla check` 21,405,002 → 21,407,798 instructions and `myla run` 24,327,287 → 24,330,096, one that imports std.io checked 39,318,652 → 39,321,814 and std.fs 43,844,540 → 43,848,216 (callgrind, `MYLA_THREADS=1`, the library the tools carry, BASE `3add216`'s tools against [[MYLA-758]]'s, 2026-11-18). A module that is only a constant costs a check nothing, where std.platform's 2,000 lines don't: with the constant read from std.platform, checking a program that imports std.fs took 48.7 M → 59.2 M instructions and one that imports std.path 26.2 M → 40.4 M; with std.path_style and the copy, 49.2 M → 49.4 M and 26.7 M → 26.8 M (`myla check` with the library the tools carry, valgrind's count, `194c9dc`'s against [[MYLA-704]]'s, 2026-11-15). It is the smallest form of choosing code per target, until [[MYLA-245]] has declarations chosen per target.

A program run, tested or checked on the machine the tools run on (`myla run`, `myla test` interpreted, `myla check`, the REPL, the language server's diagnostics) is loaded with `for_host(entry, opts)`, which is `for_target(opts, host())` ([[MYLA-723]]; the driver's `load_for_host`, after `own_library` has chosen the root): a `myla.exe` built for Windows interprets a program with Windows' std.platform (`TARGET` is `x86_64-windows`), std.path and std.path_style, as a native build for Windows takes them; on x86-64 Linux nothing changes (its `platform_file` is ""). A module a copy replaces is itself when it is the entry, so `myla test lib/std/path.my` runs path.my's cases on every host. The language server's other requests (hover, definitions) read the files as they are, where an editor shows them.

## Consequences

- `$` can't appear in source identifiers, so qualified names never collide with user names, the prelude or `Type.method` keys, and they are valid assembly labels.
- Methods need no renaming: their key is the qualified type name.
- The arguments and expected outputs of a function's `#test` attributes are renamed like other expressions, in the module's scope (the function's parameters aren't visible there), so a `#test` in an imported module can use that module's consts, structs and enums ([[MYLA-11]]).

## Entry points

The loader ([[MYLA-30]]) returns the linked program (`Loaded { decls, next_id, spans, std_impls, bodies }`), which `build_checker_lazy(prog.decls, prog.next_id, primitives, prog.std_impls, prog.bodies)` (checker) type-checks; every tool that loads a program calls it so, and the checker it returns has the bodies it read in its declarations ([[MYLA-359]]). `build_checker_std` is the same without `bodies` (a program loaded whole), `build_checker_decls` and `build_checker_with` without `std_impls` either. Its entry points:

| Function | Loads |
| --- | --- |
| `load_program(entry: str, stdlib_root: str) -> Result<Loaded, Report>` | A program without packages, rooted at the entry's directory; `stdlib_root` "" for none |
| `load_program_with(entry: str, stdlib_root: str, overrides: [str: str]) -> Result<Loaded, Report>` | The same with editor buffers (path → text), for the language server |
| `load_program_packages(entry: str, stdlib_root: str, packages: [(str, str)], root: str) -> Result<Loaded, Report>` | With packages, each (name, directory), and the project root `root` ("" for the entry's directory): what the project tool calls in-process, with each package's `dir + "/src"` and `root` `src` for files under `src/` ([[MYLA-94]]) |
| `load_program_opts(entry: str, opts: LoadOptions) -> Result<Loaded, Report>` | With every option: `LoadOptions { stdlib_root: str, packages: [(str, str)], root: str, overrides: [str: str] }`, made by `load_options(stdlib_root)` and changed field by field (the REPL and `build/myla` use it) |

`parse_package_flag(text: str) -> Result<(str, str), Report>` splits a `--package` value at its first `=`; `build/myla` (`run`, `test`, `build`, `repl`), `interp_main` and `gen_main` take the flag, and the last two also `--root <dir>`, so the burn tests (`tests/burn/test_packages.py`) can compare a nested entry with what the Python loader gave for its `project_root` (recorded, [[MYLA-219]]). How it differs from the Python loader it was ported from:

- **Node ids.** The checker keys its side tables by node id, so ids must be unique across the program: each module is parsed with `parse_ids`, which continues numbering where the previous module stopped, and the prelude is parsed last, from the loader's `next_id`. Every module keeps its own line numbers.
- **Immutable AST.** The renamer rebuilds the declarations instead of rewriting them in place; a collapsed `alias.member` chain reuses the ids of the nodes it replaces. Its first error is kept in a field (`err`) rather than returned through every call.
- **Paths.** Paths are normalized textually (`.`, `..`, repeated `/`), not with `realpath`, and existence is probed by reading the file (written before `std.fs` had directory functions, [[MYLA-88]]). So an intermediate segment need not be a directory, a directory `x/` without its root module `x/x.my` reports "cannot resolve", and a project `std` directory isn't reported as shadowing the reserved root: `std.*` simply resolves in the stdlib only. The package checks use `std.fs` (`is_dir` for a package's directory, `exists` for a project `geo` or `geo.my` shadowing a package), so those errors are the Python loader's.
- **Messages** are the Python loader's, printed as the Python CLI printed them; `tests/burn/test_selfhost_codegen.py` (`MODULE_ERRORS`) and, for packages and their errors, `tests/burn/test_packages.py` (`MODULE_ERRORS`, through `gen_main` and `build/myla build`) compare them with its recorded output.
