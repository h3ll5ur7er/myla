# Module loader

Modules are a front-end concern only: [[selfhost/loader.my]] turns an entry file and its imports into one flat list of declarations (`Loaded`) whose top-level names are unique, and the checker, interpreter and compiler never see an import. The language rules are on [[Language/Modules]].

## Steps

`load_program_opts(entry, opts)` does them with `LoadOptions { stdlib_root, packages, root, overrides }` (the other entry points are below). Without packages and a root the loader behaves as before [[MYLA-92]]. `packages` is a list of (name, directory) pairs, the `--package name=dir` flags (`parse_package_flag` splits one); `root`, the project root, is the entry file's directory when it is empty.

0. **Packages.** The list is checked first: a package named `std`, a name that isn't an ASCII letter followed by ASCII letters, digits and `_` (or is a keyword), a name given twice, an empty or missing directory are module errors without a position.
1. **Load.** Starting from the entry file, read, lex and parse each module once (keyed by its normalized path), and follow its imports depth-first, resolving each once (the module keeps its imports' targets). Every module but the entry is lexed and parsed without its `#test` cases (`parse_source_with`, `skip_tests`: the lexer skips an attribute `#test(…)[…]` unlexed, over its brackets, strings, chars, f-strings and comments, [[MYLA-359]], and the parser skips any case it still meets, [[MYLA-396]]): only `myla test` of a module's own file runs its cases ([[MYLA-360]]), and std.int has 2,042, so a module of `std` may import it at no cost. A broken case in an imported module shows only when its own file is tested. The implicit modules (below) are read lazier still ([[MYLA-359]]): their files are known before the entry is loaded (`implicit_files`, `Loader.lazy`), so also where a program or a module imports one, and so are the other modules of `std` but the entry and std.rt (`lazy_std`, [[MYLA-413]], D179 (2); a program's own modules are read whole), and `parse_module` parses them with `parse_source_lazy`, which leaves each function's and method's body unparsed (the lexer skips it, see [[Architecture/Lexer-and-parser]]) and keeps it as a site (`BodySite`: its place, its code points and node ids kept for it) beside the module's code points (`Module.sites`, `Module.cps`). `overrides` replaces a file's text with an in-memory buffer; the language server uses it for unsaved edits.
   - **The parse the toolchain carries** ([[MYLA-412]]). Such a module of `std` isn't lexed and parsed at all when its text is the one the toolchain was built with: `parse_module` asks `Loader.cached`, which finds the file's path under the stdlib root (`std/io.my`) and, when `stdroot.embedded_parse` says the text is the embedded file's (the same bytes: the built-in library, or a `--stdlib`/`MYLA_STDLIB` directory that holds the same file; an edited or another library, or an editor's buffer, is parsed as before), reads the parse kept beside it in `selfhost/embedded_std.my` (`embedded_cache`) with `astcache.decode`, its node ids moved to start at `next_id`. The parse is `parse_source_lazy`'s, written when the toolchain is built: `tools/embed/main.my`, which `scripts/bootstrap.sh` runs before stage 1 to write `embedded_std.my`, encodes each module of `std` but std.rt with `astcache.cache_entry` (the form is described at the top of [[selfhost/astcache.my]]: a string table and the declarations, numbers in printable digits, a node's id and line relative to the last one, a name the parser made of an id, `%for12`, relative to the module's first). The writer checks each entry before it keeps it: the parse at another first id is the same moved, the entry reads back as the parse, and each body read from its own text is the one read from the module's; else the module is carried without its parse (`embed` says so, and `stdroot`'s `carried_unparsed` case fails) and parsed on every use. With the parse comes, for each body left for later, where its text is in the file's bytes, so the loader keeps the module's text (`Module.src`, `Module.bytes`) instead of its code points, and decodes only the bodies it reads (`astcache.body_part`); the implicit modules' entries also hold their bodies parsed (`Bodies`, `cached_body`, which `LazyTable.read_parsed` takes before parsing the text), as every program reads some of them. A hello world's `myla check` went from 40.7 M to 20.9 M instructions (a program importing std.io 59.9 M to 36.4 M, std.http 200.6 M to 145.3 M). The parse is the one the toolchain's own parser gives only while `embedded_std.my` is current: `scripts/bootstrap.sh` rewrites it, and `test_embedded_std.py` fails when it isn't what `lib/` and the parser give; `tests/burn/test_std_cache.py` builds every example and the compiler with and without it.
   - **Implicit modules** ([[MYLA-320]], D164). Unless the entry file is a module of the standard library (`is_std_module`: under the root's `std/`, or with the embedded library under a copy of it on disk, D152's rule), `load_implicit` then loads each of `implicit_modules()` (`str`, `char`, `int`, `list`, `option`, `map`, `hash`) that the stdlib root has, `std/<name>.my` found by `descend` as an import of `std.<name>` would find it, and follows its imports; one the library doesn't have is skipped. No module's bindings get them; what they bring is their impls, whose methods need no binding. A module imported explicitly too is the same module, loaded once.
2. **Module ids.** The entry module's id is empty; every other module's id is its path, without `.my`, with every run of other characters replaced by `$`: relative to the stdlib root for the standard library (`std$io`), to a package's directory, after the package's name, for a package (`geo$shapes` for `G/shapes.my`, as if `G` were `geo/` in the project root, so no fetch path or commit appears in a name; the innermost directory wins if they nest), to the project root for the project (`geometry$geometry`), and above the project root with one `up` per level climbed (`up$up$selfhost$tokens`), so `../x.my` and `x.my` never share an id. The rules are `module_id`'s; the Python loader adopted them in [[MYLA-81]] (before, it dropped the `..` and named the standard library by its path from the project). Paths are compared as written: through a symlink, a stdlib module counts as a project module. Two paths that sanitise to the same id are an error.
3. **Exports.** A module exports its `pub` declarations as `("decl", "id$name")`; `pub from` and `pub import … as` re-exports are added in a loop until nothing changes, so chains of re-exports settle.
4. **Bindings.** For each module: its own declarations, plus what its imports bind, `("decl", qualified)` or `("module", id)`. A collision is a module error.
5. **Renaming.** `Renamer` walks every declaration and rebuilds each reference that resolves to a module-level name in its qualified form: type annotations, struct literal names, pattern type names, trait names, bounds and value references. It tracks local variable and type-parameter scopes so shadowed names stay untouched. A field chain whose prefix is a module binding (`geo.manhattan`, `a.b.c.f`) collapses into the qualified name. A dotted name in a type (`args.Spec`, D170), in an impl's trait or in a bound (`T: json.ToJson`, [[MYLA-398]]) is a module's exported type or trait (`module_type`).
6. **Merge.** All modules' declarations (minus imports) are concatenated into one list: the implicit modules first (`merge_order`), so that the checker registers their methods before a program's and a program's method of the same name on the same type is the duplicate, then the others in load order. The impls of the modules of `std` are recorded by node id with their module and file (`Loaded.std_impls`): the checker counts their methods as the standard library's code (a method on a built-in type is named after the type, `str.trim`, not `std$…`, so only its impl tells), and names the module and the place in the note of a duplicate method. The functions of every module of `std` but the entry and std.rt are recorded too, with `lazy` set (and `implicit` for an implicit module's): the checker checks their bodies only once they are called ([[MYLA-359]], [[MYLA-413]]). std.rt is read whole, as the back ends call its functions by the primitives they replace; the other functions they call by name are on `backend_std_functions`, which the checker marks as called ([[MYLA-432]]). A native build's program has tasks (`Checker.task_line`, D90) where an `async let` is in any body loaded, read or not (`LazyTable.task_line`, `async_let_in`), so that it is built as when every body was read. The bodies their parse left (`LazyTable.add`, by `body_key`: the declaration's id, an impl's for a method, and the line and column of the body's `{`, whose limits the lexer tested, [[MYLA-416]]) go to the checker as `Loaded.bodies` (`LazyBodies`), whose `parse` reads one when the checker first checks it (`LazyTable.read`): `parse_body` lexes and parses its code points with the node ids kept for it, so its nodes are in its module's range of ids (`file_of` finds the file, a debugger the line), and the module's renamer, kept for it, renames it with the names in scope there, as `Renamer.function` would have (the parameters, `self` in an impl, the type parameters and `Self`). A lex, parse or module error of a body read so is reported where it is, with its kind (`kind_of`), when a program calls the function; one no program calls shows only in the module's own `myla test` or `myla check`, which parse the whole file, as its type errors do, and `scripts/update-seed.sh` checks the eight implicit modules so (D179). When the entry file is itself a module of `std` (`myla test lib/std/task.my`), whose names stay unqualified as an entry's do, its functions are recorded too, with the module's dotted name (`std_module_name`): that is how the checker knows its `cancel` for `task.cancel` ([[MYLA-388]]).

Path resolution (`resolve`) uses the leading-dot count: none means the project root, then the stdlib root; one dot the importer's directory; each further dot one level up. The last segment is a file `x.my` or a package `x/x.my`. Without dots the first segment decides: `std` resolves in the stdlib root only (the Python loader also reported a project `std` as an error, see below); a package's name in its directory only (`resolve_in_package`: `geo` is `G/geo.my`, `geo.b.c` is `G/b/c.my` or `G/b/c/c.my`), and a project `geo.my` or `geo/` is then an error, `'geo' is a dependency and cannot be shadowed by a project file or directory`, raised at the import like the `std` one; any other name in the project root, then the stdlib root ([[Language/Modules]]).

The standard library root is a directory (`--stdlib`, `MYLA_STDLIB`), or by default `<myla>`, the library the toolchain carries ([[MYLA-243]], [[selfhost/stdroot.my]]): its files `<myla>/std/io.my` are read from memory (`source_text`: an editor's buffer first, then an embedded file, then the disk), so resolving, module ids and diagnostics work the same as for a directory and no file is written on any platform.

## Consequences

- `$` can't appear in source identifiers, so qualified names never collide with user names, the prelude or `Type.method` keys, and they are valid assembly labels.
- Methods need no renaming: their key is the qualified type name.
- The arguments and expected outputs of a function's `#test` attributes are renamed like other expressions, in the module's scope (the function's parameters aren't visible there), so a `#test` in an imported module can use that module's consts, structs and enums ([[MYLA-11]]).

## Entry points

The loader ([[MYLA-30]]) returns the linked program (`Loaded { decls, next_id, spans, std_impls, bodies }`), which `build_checker_lazy(prog.decls, prog.next_id, primitives, prog.std_impls, prog.bodies)` (checker) type-checks; every tool that loads a program calls it so, and the checker it returns has the bodies it read in its declarations ([[MYLA-359]]). `build_checker_std` is the same without `bodies` (a program loaded whole), `build_checker_decls` and `build_checker_with` without `std_impls` either. Its entry points:

| Function | Loads |
| --- | --- |
| `load_program(entry: str, stdlib_root: str) -> Result<Loaded, Report>` | A program without packages, rooted at the entry's directory; `stdlib_root` "" for none |
| `load_program_with(entry: str, stdlib_root: str, overrides: [str: str]) -> Result<Loaded, Report>` | The same with editor buffers (path → text), for the language server |
| `load_program_packages(entry: str, stdlib_root: str, packages: [(str, str)], root: str) -> Result<Loaded, Report>` | With packages, each (name, directory), and the project root `root` ("" for the entry's directory): what the project tool calls in-process, with each package's `dir + "/src"` and `root` `src` for files under `src/` ([[MYLA-94]]) |
| `load_program_opts(entry: str, opts: LoadOptions) -> Result<Loaded, Report>` | With every option: `LoadOptions { stdlib_root: str, packages: [(str, str)], root: str, overrides: [str: str] }`, made by `load_options(stdlib_root)` and changed field by field (the REPL and `build/myla` use it) |

`parse_package_flag(text: str) -> Result<(str, str), Report>` splits a `--package` value at its first `=`; `build/myla` (`run`, `test`, `build`, `repl`), `interp_main` and `gen_main` take the flag, and the last two also `--root <dir>`, so the burn tests (`tests/burn/test_packages.py`) can compare a nested entry with what the Python loader gave for its `project_root` (recorded, [[MYLA-219]]). How it differs from the Python loader it was ported from:

- **Node ids.** The checker keys its side tables by node id, so ids must be unique across the program: each module is parsed with `parse_ids`, which continues numbering where the previous module stopped, and the prelude is parsed last, from the loader's `next_id`. Every module keeps its own line numbers.
- **Immutable AST.** The renamer rebuilds the declarations instead of rewriting them in place; a collapsed `alias.member` chain reuses the ids of the nodes it replaces. Its first error is kept in a field (`err`) rather than returned through every call.
- **Paths.** Paths are normalized textually (`.`, `..`, repeated `/`), not with `realpath`, and existence is probed by reading the file (written before `std.fs` had directory functions, [[MYLA-88]]). So an intermediate segment need not be a directory, a directory `x/` without its root module `x/x.my` reports "cannot resolve", and a project `std` directory isn't reported as shadowing the reserved root: `std.*` simply resolves in the stdlib only. The package checks use `std.fs` (`is_dir` for a package's directory, `exists` for a project `geo` or `geo.my` shadowing a package), so those errors are the Python loader's.
- **Messages** are the Python loader's, printed as the Python CLI printed them; `tests/burn/test_selfhost_codegen.py` (`MODULE_ERRORS`) and, for packages and their errors, `tests/burn/test_packages.py` (`MODULE_ERRORS`, through `gen_main` and `build/myla build`) compare them with its recorded output.
